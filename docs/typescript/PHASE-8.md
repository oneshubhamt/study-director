# Phase 8 · F33 parity and the SDVC1 build

**Planned for after Phase 7.** All deployed devices already run F33. F33 defines the product behavior and existing data SDVC1 must support. The certified post-Phase-7 TypeScript application supplies the implementation and its independently acquired safeguards. The deliverable is a verified, reproducible SDVC1 deployment package built from the reconciled TypeScript source. Distribution and promotion to `main` are separate owner decisions.

Read the [source audit, version matrix and commit index](PHASE-8-INTAKE.md) alongside this roadmap. The intake records the starting evidence. P8.0 must repeat the comparison on the actual Phase 7 exit SHA. Follow the [execution discipline](../../AGENTS.md), [decision D-15](DECISIONS.md), [verification procedure](../VERIFICATION.md) and [test programme](../../tests/README.md).

## Owner decisions for parity

The owner confirmed F33’s Drive Disconnect behavior on 2026-11-25. Disconnect ends the connection on the initiating device and preserves the Google account grant. P8.2 must assert zero OAuth revocation calls, including during an active sync, and prove that a second connected device can still sync. Record any other disputed F33 behavior in its own ledger row. Bring the specific alternatives, observations and user impact to the owner in the affected pass before changing that behavior.

## P8.0 · Freeze the inputs and turn history into a worklist

1. Record the Phase 7 certification, its exact source SHA, retained artifact and any limitations. Pin F33 at `d69f2053629a7e24d106a969f0d69eac65b4996b`. Check the release identifiers in both source and built manifests. If a later release appears on `main`, list it separately for the owner. A moving ref must never silently change the F33 target.
2. In disposable checkouts build F33 and the Phase 7 baseline with each checkout's lockfile, toolchain and normal entry points. Retain runnable reference builds, manifests and checksums. If an actual deployed F33 package is available, compare its asset inventory, identity and headers with the reconstructed reference and record which one drove upgrade tests. Isolate browser profiles and provider repositories from production accounts and data.
3. Generate two complete Git inventories. Set `T` to the full certified Phase 7 SHA. These commands run from the repository root.

   ```sh
   F=d69f2053629a7e24d106a969f0d69eac65b4996b
   T=${PHASE7_SHA:?set PHASE7_SHA to the certified commit}
   B=$(git merge-base "$F" "$T")
   git merge-base --all "$F" "$T"
   git rev-list --left-right --count "$F...$T"
   for end in "$F" "$T"; do
     git log --reverse --topo-order --format='%H %P %s' "$B..$end"
     git log --first-parent --reverse --oneline "$B..$end"
     git diff --name-status --find-renames "$B" "$end"
     git log --full-history -m --name-status --find-renames "$B..$end"
   done
   ```

   Check the base against the intake. Inspect integration commits against their parents for merge-only edits. Include removed, renamed and later-reverted files, QA helpers, contracts, docs, builds, styles and generated files. A final-tree diff loses intermediate decisions. Pair a generated delta with its authored producer and the artifact it ships.
4. Maintain a durable ledger in the phase handoff. Assign stable IDs and these fields to each distinct outcome.

   | Origin commits and paths | F33 behavior and failure prevented | TS owner, callers, emitted entry and TS-only invariant | Disposition and reason | Red/baseline evidence | Candidate evidence, SHA and status |
   | --- | --- | --- | --- | --- | --- |
   | One or more commits, both directions where applicable | Input, action, expected UI, durable state or forbidden side effect | Include the real boot, event or storage path | Missing, equivalent, overlapping, TS improvement, structural, historical, or explicit product decision | Command and observed result, or identified gap | Assertion, artifact/run and remaining limit |

   Map every inventoried commit and changed path to at least one row or a reasoned structural, historical or superseding entry. One commit can feed several rows. Group mechanical conversions by producer and checked output. Preserve TS-only semantic fixes in separate rows even for features with zero F33 path changes. Reconcile the sets in both directions by machine and inspect the reasons by hand. Keep unmatched IDs, paths, requirements and untested behaviors visible. A count of matches, a green old suite or a familiar filename cannot close a row.
5. Run representative reference journeys and establish which outcomes the Phase 7 baseline already satisfies. Record the input, clock, files, profile, provider state and expected observables before editing. For flaky or conflicting evidence preserve the first failure, isolate the cause and rerun. Distinguish a broken source extractor from a product failure. Where F33 has a known defect and TS has a demonstrated correction, record both behaviors and retain the correction. Escalate a genuinely unresolved product choice with both reproductions.

**Exit** when the two inventories reconcile to the ledger, reference builds run, and each open row has an owner, a pass and an observable acceptance condition. P8.0 delivers the baseline and worklist. Product edits begin in P8.1.

## Implementation passes

Work one outcome at a time. These boundaries group interdependent work. When a cross-feature fix is needed, update all callers and assign its end-to-end regression to one pass, with dependencies recorded in the other. Use one typed implementation per behavior. Keep source validation, authority checks, type/lint gates, worker boundaries and build provenance in force. Read F33 source and history for intent, then implement in the current typed owner. Merge ancestry and a mechanically resolved diff confer no parity credit.

## Real F33 upgrade and mixed-device matrix

Use values emitted by the F33 app through normal saves, export and backup. Record release/build IDs, fixture origin, sanitized fixture characteristics and digests. Never use personal production data or modify an owner's live repository for these tests. A synthetic malformed sample can supplement genuine F33 output.

| Starting condition | Required observation |
| --- | --- |
| Fresh SDVC1 and populated F33, updated **in place at the same origin and scope** | IDB, localStorage, OPFS, Cache Storage and profile binding survive switch, reload, offline reopen and a second tab. Compare profile IDs, records/dates, notes/links, saved plans, preferences, pending reviews/deletions, active owner/status and attachment names, sizes and byte digests. Check no unexpected mutation on read or startup. |
| F33 backup file, password-protected file, managed Device Folder and Drive checkpoints | Restore into a clean candidate, then edit, save, re-export and read back. Include empty, populated and large cases, duplicated attachment content under distinct identities and remotely missing assets. Check manifest, version, authority, tombstones, provenance and logical content, allowing only documented nondeterministic fields. Wrong password, corrupt/truncated input, quota and permission loss leave previous data recoverable. |
| Interrupted restore or sync, separate windows, process restarts | Inject interruption before commit, after write, after verification and before journal cleanup. Inspect journal state and both stores on reopen. Denied or lost ownership prevents mutation. Verified incoming content survives. Earlier incomplete phases restore the known-good safety copy. A failure to verify or finish remains visible and retryable. |
| F33 and SDVC1 online together during rollout | F33 edits → candidate reads → candidate edits → F33 reads. Exchange active and finished sessions, claim transfers, protected checkpoints, saved days, note identity/links, reflection changes, conflicts, deletions and files. Include simultaneous edits, device sleep, expired auth, offline reconnect, local disconnect and sign-in to the wrong account. Check no unauthorized access, silent clears, duplicate rows, stuck claims or stale overwrite. |
| F33 page/controller beside an updating SDVC1 client | Exercise old tab open, dirty editor, offline first reload, interrupted asset fetch, unknown client, safe update and cache cleanup. Verify page, worker, assets and scoped clients agree on identities, dirty input survives and both releases keep required assets while in use. Check cold launch after the old tabs close. |
| Rehearsed rollback on disposable data | Reopen F33 with a candidate-written copy and test real F33 reads, writes, sync and affected UI. Preserve an independently verified pre-upgrade backup, the prior package and restoration steps. If bidirectionality fails, identify exactly which data would be lost, stop mixed writes/promotion and obtain an owner decision on rollout and recovery. A shell downgrade alone proves nothing about data written by SDVC1. |

One canonical F33-compatible format is the intended result. Development-only `ts-exp` data has no migration requirement. An unexplained rejection of valid F33 data, a lossy decode, or dependence on installing an older release blocks closure. Preserve fail-closed behavior for unsupported or damaged input. Do not ship a historical reader, hidden rewrite or fallback that manufactures empty data.

## P8.6 evidence and release gate

1. A reviewer starts again from F33, Phase 7, the common ancestor and the final candidate. Walk authored source → registered owner → normal user entry → durable result → shipped code. Sample high-risk items independently of the implementor's chosen tests. Account for every F33 change, every retained TS-only correction and every item introduced during reconciliation. Check that previously equal behaviors still hold after all ports.
2. Confirm `release.config.mjs` as the release authority for **SDVC1**. Set the reproducible epoch/build identity under the release procedure. Inspect derived release/build/asset IDs in development, deployment, minified Firebase stage, legal surfaces, manifest, SW cache keys/messages and diagnostics. Check the cross-release parser and controller by running F33 and SDVC1, including existing cached assets. Verify source commit provenance, public inventory, CSP, headers, OAuth configuration and absence of private fixtures or development helpers in the public package.
3. Run post-change promotion gates on the exact final source. At planning time `npm run qa:promotion` covers strict types/lint, fast tests, source and branch coverage, mutation, release/build/minification/performance and browser coverage. Use the Phase 7 successor commands if tooling has changed. In hosted Promotion QA enable the browser option and inspect all required jobs and results. Reconcile the suite registry against executed browser tiers and run any remaining required release/feature/extended, maximum-capacity and isolated performance selections. Follow repository repeat and isolation rules. Preserve budgets, permissions, test strength and generated-runtime reproducibility.
4. On staged SDVC1 repeat critical data, auth, session, Notes and PWA journeys. Record actual browser/device/OS, provider and artifact. Include desktop Chromium, supported mobile/tablet behavior, physical installed iOS/Safari, offline/restore and real Drive sign-in/expiry/disconnect with designated test profiles and permission to use them. Distinguish simulated providers from live ones and mobile emulation from physical evidence. A missing device or credential keeps the corresponding certification open. Record known F33 failures separately from candidate regressions and establish their exact effect before claiming parity.
5. Rebuild twice from the clean final SHA, lockfile, pinned toolchain and same release inputs. Compare payload file hashes, manifest, package contents and served bytes. Record the exact archive or deployable directory, digest/inventory, source SHA, release/build/asset IDs, run links, reference fixture digests, manual results, open exceptions and rollback results. Any post-test code, configuration or output change invalidates the affected evidence. Preserve evidence with the repository's normal release handoff. Production distribution requires a separate owner decision.

**Closure** requires a deliverable SDVC1 package, completed F33 upgrade and coexistence evidence, both ledgers reconciled, every mandatory result green on the candidate and explicit disposition of material deviations. A failing, skipped or unavailable mandatory check leaves certification open. Report package preparation, certification and deployment as separate states.
