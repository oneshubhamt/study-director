## Intake and design review

F33's backlog says steps 1–3 shipped and step 4 paused at 4a. Its detailed plan also marks historical-format test retirement (C3) complete in F30 and Insights timing work (D7) done. These are statements about F33. On the planning TS head `f415f0a9`, the generated-case helper, timer and retention tests, coverage floors, mutation runner and browser isolation registry already exist. The push workflow still selects targeted tests. F33's description of a whole-fast-suite push workflow cannot establish TS coverage. [F33 backlog](https://github.com/oneshubhamt/study-director/blob/d69f2053/docs/backlog.md#test-suite-programme-approved-by-the-owner-on-2026-11-02) · [Original objectives, ground rules and step 4 register](https://github.com/oneshubhamt/study-director/blob/d69f2053/docs/test-programme.md)

Three findings change how to execute the original plan.

- **A failing process can give false mutation evidence.** Both branches' mutation runners credit a nonzero test status. A broken loader, missing dependency or unrelated assertion can therefore look like a successful kill. Before retiring a guard, run the unchanged control in the same disposable environment, apply one unique mutation to the actual executed owner, and identify the intended failing assertion. An unrelated failure is inconclusive. Exercise the runner itself with a surviving mutant, an intended kill and a setup failure. Preserve the failing test, reason and replay command.
- **Consolidation can remove useful isolation.** TS's browser registry records standalone execution for encryption, update, handoff and performance journeys. Merge only shared setup with compatible isolation, tiers and failure modes. Keep scenario names, assertions, tags, fresh state and individual selection. Preserve a separate stress or performance run when a shared setup would warm caches or hide a leak. Compare runtime on the same machine and inputs. F33's file counts and timing estimates are historical measurements, never deletion targets.
- **Source checks serve different purposes.** Keep checks where structure is itself the contract, including authority boundaries, data-key inventories, privacy, generated provenance, CSP and supply-chain constraints. Replace behavioral source checks with assertions on a real module or built app. Verify both the visible result and durable writes or forbidden side effects. A deleted historical-name ban needs a documented retired owner and confirmation that no live boundary depended on it. A typed mock compiling cannot establish parity with its production provider.

## Whole-suite design and efficiency

The objective is to find consequential mistakes quickly and explain them well. Evaluate each feature's contract and failure history before choosing an assertion or test layer. The remit includes unchanged and already typed tests, fast and browser tiers, fixtures, generators, mutation and coverage tooling, and CI scheduling.

### Findings from the typed suite

At `e0132da4`, the discovery helper selected 169 fast files (32 unit, 104 integration and 33 architecture). The tracked test tree occupied 3,960,402 bytes by file contents. Two integration files alone, `sync-shared-base.mjs` and `repository-checkpoint.mjs`, accounted for 436,340 bytes. Searching architecture source for literal calls to `assert.match` and `assert.doesNotMatch` returned 1,221 occurrences. This is a triage signal. Some matches protect real build, security or ownership requirements. The aggregate gives no estimate of removable checks or runtime saved.

One local run of `node tests/helpers/run-category.mjs fast` on this application/test head passed all 169 files with two jobs in 112.3 seconds (runner time). The slowest files were repository checkpoint (44.1 s), repository restore (24.7 s) and sync shared base (12.1 s). File times overlap. Profile setup, cryptography, real waits and repeated workflow execution in those paths before trading away any data-safety scenarios. This single sample establishes neither a typical CI duration nor a speedup.

- **Tests that reward the wrong outcome.** The backup recovery UX contract matches HTML containing “While signed in” and exact adjacent tags. The managed recovery contract matches provider wiring and function text. A harmless markup refactor can break the first check. Correct-looking source can coexist with an upload running during recovery. Exercise the actual recovery entry with a controlled provider, verify pause, refusal of competing writes, and resumption after success and failure. Keep a direct UI assertion where users need an accessible name, a decision with data-loss consequences, or a truthful status. Assert the role, available action and outcome. Require exact prose only where the wording itself is a product requirement.
- **Generated inputs can change on replay.** The current `checkCases` helper enumerates the selected seeds and passes their position to the callback. In a two-seed probe the second seed received index 1 in the series and 0 on individual replay. The sync-merge witness uses that argument in installation IDs and retention uses it in case data. P6.1 must preserve the complete input and operation trace on individual replay. Verify identical serialized inputs for a non-first seed. Record the scenario name, seed and shortest known failing sequence. Promote a small reproducible counterexample into a named regression when appropriate.
- **The execution graph repeats real work.** Local promotion calls the fast suite, then line coverage executes unit and integration again. The default branch-coverage path executes unit and integration again. Both local promotion and the hosted promotion workflow invoke these three stages separately. The runners already support retaining raw V8 output and passing it to branch coverage with `--from`. Verify that the recorded unit/integration evidence can serve all intended gates while keeping architecture execution and hermetic conditions intact. The release chain also calls strict checks already invoked by local promotion. Trace which jobs use the same SHA, inputs, toolchain, instrumentation, generated assets and isolation. Reuse eligible results in the same run, with clean uninstrumented runs for timing or instrumentation-sensitive behaviors. Before removing an invocation, demonstrate identical discovered test IDs, assertions, denominators, coverage floors, failure propagation and artifact provenance. An architecture suite excluded from a coverage pass still needs an execution owner.

### Design each scenario from the failure it should detect

| Family | Inputs and independent expected outcome | Fault that should fail the witness |
| --- | --- | --- |
| Insights and aggregates | Hand-calculate a short history containing an empty day, a gap, ties and a partially completed day. Check full-window totals against disjoint subtotals, rate denominators including zero, boundary inclusion and presentation rounding. Compare worker and fallback with the independent expected values. | Drop a boundary day, average averages with unequal weights, or count missing data as zero. Two paths sharing the same arithmetic can agree on a wrong answer. |
| Timers, schedule and study day | Use a small reference timeline with explicit units, event order and the configured day boundary. Partition elapsed time into disjoint categories. Exercise just before, at and just after a transition, pause/resume, app sleep, clock rollback and restore. | Double-count a paused interval, lose elapsed work on reload, or assign an event to the wrong study day. |
| Save, sync and retention | Use a small state-transition table for local edit, remote edit, conflict, resolve, retry and deletion. Check idempotence on repeated operations and conservation of both competing values under the documented conflict rule. Compare retained checkpoints and reachable asset IDs with a small independent example. | Resolve twice and lose an edit, delete an object still reachable from a kept checkpoint, or publish twice after retry. |
| Journals, attachments and ownership | Inject a failure before and after a durable write, interrupt and reopen, or lose ownership during an await. Compare records, bytes, outstanding journals, forbidden writes and visible outcome against the current TS contract. | Show success after partial persistence, allow a stale completion to overwrite newer work, or delete another note's attachment. |
| User journeys and accessibility | Exercise one normal built-app path from user action to visible state and reload. Include meaningful keyboard/focus and denied-action behavior. Put combinatorial variations in the lowest layer that faithfully exercises their owner. | Correct domain code wired to the wrong control, an inaccessible recovery action, or a success notice before data survives reload. |

Use exhaustive enumeration for small state spaces, boundary partitions for numeric inputs, and seeded operation sequences for larger state spaces. For a dangerous interaction, explicitly cover the combination that causes loss, even when a pairwise sample would miss it. Declare each law's preconditions (order-independent totals, for example, differ from order-sensitive histories). Prefer a hand-worked answer or simple independent model. Avoid constructing expected values by calling the production algorithm under test. Distinguish integers, durations and exact counts from floating-point estimates; justify any tolerance from the contract.

### Measure and simplify in the existing passes

1. **P6.0:** For each area, map material failure modes to the cheapest faithful witness and identify gaps, overlap, incidental wording checks and expensive setup. Group mechanical equivalents. Give safety-critical removals individual evidence. Benchmark fast, coverage, mutation and browser tiers separately on a fixed SHA with pinned tools, explicit job count and cold/warm conditions. Record wall time, slowest files, repeated process/browser/build starts and retry history. Use comparable repeated samples for before/after claims. Measure hosted critical-path duration separately from aggregate job minutes.
2. **P6.1–P6.5:** Prioritize false-green safety checks, then measured costs. Remove a trivial phrase pin with a stated reason; preserve an accessible label or material warning through the UI where needed. Consolidate shared expensive setup only where cases keep independent state and attributable failures. Split monoliths by distinct contracts when it improves targeted execution. Evaluate the current size-based scheduler against observed timings before changing it. Keep browser isolation, deterministic cleanup and ordinary offline execution. Avoid an exhaustive browser permutation suite when model tests plus a representative end-to-end witness detect the same faults.
3. **P6.6:** Deliver a before/after table for feedback time, promotion critical path, expensive repeated work, retained safety floors, representative mutants and defects found. List the major removed checks with rationale, genuinely missing scenarios added and remaining high-cost tests with reasons. Demonstrate unchanged control passes, intended fault detection and repeatability. If a tier grows slower to cover a real gap, quantify the cost and record the tradeoff. Historical file counts, assertion counts and line coverage alone cannot close this objective.
