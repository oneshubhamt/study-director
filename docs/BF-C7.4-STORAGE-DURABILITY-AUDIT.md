# BF-C7.4 — Storage durability verification

**2026-11-05 · Study Director `bug-fixes` · SDVB75F23 · audit-only.** Baseline: current source after BF-C7.1–C7.3. Audit and targeted tests only; **no change to any production source**, IndexedDB store/field, OPFS layout, backup format, migration or synchronization topology. Evidence: [CI 42004706366](https://github.com/oneshubhamt/study-director/actions/runs/42004706366), source-checked. Findings below refer to *actual current source*, not an earlier completion claim.

## Objectives and verification gates

1. **Current source inventory:** trace authoritative writes, strict/default IndexedDB policy, commit barrier, local rescue, positive read-back, failure response and crash window for each data family.
2. **Adversarial targeted QA:** test pending autosave, failed strict IndexedDB transactions, falsely early success, OPFS staging failures and corruption, interrupted restore, quota/storage denial and simulated reload/recovery. Distinguish hermetic simulations from genuine browser/device testing.
3. **Disposition:** document demonstrated gaps, impact, confidence, and separately approvable repair paths. Do not replace existing persistence architecture or add a blanket strict-write policy.

## Findings by impact, not by speculative implementation

1. **F1 — Moderate, expected, actionable only if the product standard changes.** `save-lane.js` and the Plan draft debounce leave a bounded latest-edit window. Contrary to the SDVB74J write-up, Note rescue is not persisted at every first keystroke; it is an explicit failed-save/page-exit safety net. A hard kill without `pagehide` can lose the last uncommitted keystrokes. No evidence of silent loss of older **committed** notes. **Possible separate proposal:** measured per-key precommit rescue or visibility-based flush, with quota/write-amplification/privacy costs and tests; do not implement casually.
2. **F2 — High impact, external failure domain rather than a code defect.** Deleting site data/profile, hardware loss or corrupting the entire origin can remove IDB, OPFS **and** rescue copies. *Protected* reduces browser eviction, not these failures. **Required operational defense:** at least one independently verified Device Folder, Drive or external backup; periodically restore a disposable copy. A Device Folder on the same failed disk does not diversify hardware risk.
3. **F3 — Low to moderate, already correctly guarded but browser-sensitive.** `{durability:'strict'}` is requested selectively and may fall back to default where browser support is absent; a requested hint is not proof of physical fsync. The fallback is logged under `storage.idb-strict-durability-unavailable`. Physical browser/OS crash testing is still needed before claiming strict disk-flush guarantees on each target platform.
4. **F4 — Low for normal operations, high-impact only under catastrophic storage failure.** OPFS bytes and IDB metadata are distinct transactional systems. Verified staging + strict metadata + orphan cleanup gives good ordering, but no atomic commit spans both. No new topology is justified absent a reproduced inconsistency; retained attachment integrity audits and independent backups matter more.
5. **F5 — Low/medium capacity boundary with honest warnings.** Rescue copies are bounded (`localRescueBytes=4 MiB`, `noteRescueBytes=1 MiB`, `fallbackDailyRecordsBytes=3 MiB`). They are emergency cushions, not full-history archives. If the browser is simultaneously unable to write IDB and the rescue budget is full, the app retains volatile text and reports what cannot be saved: keeping the tab open and exporting/backing up is essential.
6. **F6 — Not a demonstrated defect; outdated baseline assumptions.** Independent Reflection Draft persistence has been retired. Device A/B file rotation and five Drive versions do not describe the current managed-repository retention model. Do not design fixes or release claims from those historical descriptions.

## Disposition / next decisions

- **Source/logic audit: COMPLETE.** No verified missing strict transaction at a critical canonical write. No demonstrated reason for blanket additional strict writes, new journal topology, schema migration or CRDT-style storage redesign.
- **Hermetic failure matrix: PASS.** The new and pre-existing tests establish the behaviors enumerated above; independent CI build/deployment gates passed.
- **Real-browser and physical acceptance: OPEN.** Use disposable profiles to run `tests/browser/storage/storage-failure-recovery.mjs`, `site-data-clear.mjs`, `multi-tab.mjs`, backup restore and attachment suites in an actual supported browser. Repeat on Safari/macOS, Android PWA and iOS where feasible. Use an independently restored backup to verify byte-for-byte study/attachment content. External power-loss and disk-loss scenarios need a carefully controlled test environment; never risk the user's real profile.
- **Production fixes require explicit separate approval.** If the owner wishes to reduce the latest-keystroke crash window, first measure failures and capacity trade-offs; otherwise leave current CLEER architecture unchanged.
