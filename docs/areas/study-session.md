# Study session

Today's study session (the Active Session) and its timer: what is stored, which device runs it, and how it moves between devices. Timer sounds and reminders are in [notifications.md](notifications.md).

## The Active Session

The Active Session is portable across devices and backups. It carries the current session/schedule/review state required to resume work, and the installation running it (`runningOn`, ActiveSession v10; an older session belongs to the installation that converts it). A restored running or paused timer is rehydrated into the timer runtime only on the installation it names, and the Execute controls are then derived from that restored runtime. Any other installation shows the session as running on another device and runs it only after Continue Here (below).

The Plan working draft and the applied Active Session schedule are separate state. Restoring or continuing a session applies the session's canonical schedule directly; it never writes that schedule through Plan-draft persistence and never enters Plan editing. Any local Plan draft remains exactly as authored. After a handoff the board stays in the applied/live state until the person explicitly chooses to edit, at which point the preserved draft is available.

## Across devices

Decisions (owner, 2026-10-18):

- The session names the device running it; only that device runs the timer. Another device shows "Running on another device" and edits notes and everything else freely; notes from it reach the running device without stopping its session.
- Suspend hands the session over: it uploads at once and the other device offers Continue here.
- Continue Here and Restore Session sit in Execute's status card and in the session strip above the Plan board, in one order: next step, Suspend, Finish, Reset last. Controls that cannot act are hidden, not disabled. Continue Here on a device whose copy still runs elsewhere asks first; the device taken over from stops at its next sync and keeps its unsynced progress for review.
- "Needs review" opens during a running session and leaves the session as it is.

How Continue Here shows its steps and errors: [status-indicator.md](status-indicator.md#continue-here).

**How sync treats it.** The session names the device running it (`runningOn`, the installation id), and only that device runs its timer. Another device keeps a copy it never runs and shows "Running on another device"; notes, Saved Days and everything else work there as usual. Ordinary reconciliation still uses the exact canonical Active Session fingerprint stored in the shared reconciliation baseline. The lightweight Drive ownership claim is a separate control-plane fact: while its newest applicable epoch names this device, an older checkpoint naming the previous owner cannot hand execution back.

Ownership metadata and study content are deliberately different reconciliation domains. The Active Session codec defines a semantic content projection containing the date, applied schedule and study evidence while excluding `runningOn`, status, session/content/save revision counters and persistence timestamps. Continue Here binds its ownership claim to a SHA-256 fingerprint of exactly that semantic content. A pure ownership transition therefore creates no false content conflict. If the old owner later publishes study evidence that differs from the handoff boundary, sync can distinguish one-sided continuation from genuine two-sided divergence; genuine divergence is kept for review rather than discarded.

A Saved Day and an Active Session use related revision numbers, but those numbers are **not cross-device ancestry identifiers**. Save Today records the current session content revision in the Saved Day and, on that same session lineage, advances `ActiveSession.snapshot.savedRevision` before persisting the session again. On a later launch, a previous-day Active Session is retired quietly only when its own `savedRevision >= contentRevision` and the canonical Saved Day for that date exists. Sync does not infer that one device's Saved Day covers another device's session merely because their numeric counters compare. If the remote side has a newer Saved Day and no Active Session, that explicit end-of-session state outranks the ordinary running-session hold rule; any genuinely divergent local session content is kept for review before the stale recovery row is retired.

## Moving a session

Active Session content and ownership are separate. Continue Here first flushes the independent Plan draft, then reads the newest verified Drive head **without running general sync**: it verifies the head manifest/commit and opens only the repository object containing the Active Session. The local and verified-shared semantic content fingerprints must match; if Drive has newer study content, Continue Here stops and schedules ordinary sync so notes, Saved Days, attachments and session evidence reconcile through their normal transaction.

If the content matches, Continue Here acquires a new monotonic Drive ownership epoch through the protected **v3** claim. The claim contains opaque session/owner tokens plus a SHA-256 fingerprint of the exact semantic session content observed at handoff; no schedule, progress, device id or date is stored in plaintext. Under the publication lease, Drive's head is re-listed and must still be the exact verified checkpoint that was observed before the claim is written. Only after the claim is durably read back does this device strictly save and read back the new local owner session; only then may its timer run. A failed local commit writes a newer compensating ownership claim when that rollback can be verified. If compensation itself cannot be verified, the handoff fails closed and the timer does not start; reloading/retrying resolves the durable claim rather than pretending ownership is known.

The newest applicable ownership epoch remains authoritative until a later verified epoch supersedes or explicitly releases it; it does not expire by time. An open old owner checks the lightweight claim about every 15 seconds, flushes its latest progress, freezes only its runtime clock, and forces Drive catch-up; canonical progress remains untouched so ordinary reconciliation can keep any divergence for review. Older claim files are compacted best-effort after a successful full checkpoint. Suspend and plan-apply still publish urgently through the normal shared checkpoint path.

## When this device loses the session

When a verified lightweight Drive claim shows that this device no longer owns its running Active Session, Study Director stops its local execution loop immediately and preserves the frozen timer/practice evidence. The local draft must commit through strict canonical IndexedDB storage and pass a matching strict read-back before claim-triggered sync starts. Failure, null result and emergency local-only rescue are **not** declared canonical; the page retains a persistent safety warning and retries through its existing 15-second claim watcher. A managed-recovery preflight still independently rejects unverified snapshots; it can incorporate later Session reflection edits without adding time spent frozen. If the claim returns to this device, the runtime resumes only when the frozen state was saved and the TimerEngine actually resumes. No guarantee of recovery exists when every browser storage surface is unavailable and the page is terminated; keep the page open and heed the warning. BF-1 advanced only the lightweight shared ownership-claim protocol to v3; the canonical Active Session schema itself is unchanged.

The visible/eligible Active Session claim watcher keeps its **15-second** cadence and the parallel remote claim/strict local session reads. A confirmed-offline browser avoids futile Drive claim reads; returning online or making a hidden tab visible can immediately perform a missed eligible check. Those event-driven wakes use the same single interval owner's 15-second attempt throttle and the check's existing in-flight guard. Explicit claim verification remains independent of the wake throttle so a failed frozen-session local write can still retry through the normal direct path. This is **open-app cooperative work**, not a closed-app OS background service, and remote handoff cannot be observed while truly offline.
