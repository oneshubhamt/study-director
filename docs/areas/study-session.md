# Study session

Today's study session (the Active Session) and its timer: what is stored, which device runs it, and how it moves between devices. Timer sounds and reminders are in [notifications.md](notifications.md).

## The Active Session

The Active Session is portable across devices and backups. It carries the current session/schedule/review state required to resume work, and the installation running it (`runningOn`, ActiveSession v10; an older session belongs to the installation that converts it). A restored running or paused timer is rehydrated into the timer runtime only on the installation it names, and the Execute controls are then derived from that restored runtime. Any other installation shows the session as running on another device and runs it only after Continue Here (below).

The Plan working draft and the applied Active Session schedule are separate state. Restoring or continuing a session applies the session's canonical schedule directly; it never writes that schedule through Plan-draft persistence and never enters Plan editing. Any local Plan draft remains exactly as authored. After a handoff the board stays in the applied/live state until the person explicitly chooses to edit, at which point the preserved draft is available.

**Plan board and save contract (BF-C5).** The board label and styling describe the content actually rendered: when an applied schedule exists and editing is closed, it stays LIVE even if the independent working draft is ready, incomplete or invalid. The Edit Draft control also identifies a separately authored invalid or empty draft instead of implying that it edits the live Plan. Explicit editing (or having no applied schedule) shows the draft's own state and validation. A silent preview during startup, restoration, import, reset or ownership change never replaces session feedback with an unrelated draft error. Cancel closes editing without replacing the draft; any queued preview is cancelled. User-initiated Apply/Done waits for one successful strict IndexedDB Plan-draft write before changing the applied schedule; a failed save or an intervening edit stops application without losing the previous live schedule. An unchanged live-plan reapply does not duplicate that write. Reapplying an already-canonical Active Session is deliberately synchronous, writes no working draft, and preserves its existing content.

**BF-C6.1 — Authoring and Cancel lifecycle (2026-11-05).** Plan Composer text, not delayed or previously rendered row memory, is the authority for Done. Confirm parses and renders that exact current text, rejects incomplete/invalid content without rewriting it, and strictly saves it once before any applied-schedule transition. The 220 ms preview only reads the latest text *when it fires*, and structured row edits cancel it; no cached preview may overwrite newer edits. Any pending Done or replacement/break confirmation is conditional on the same editor epoch: Cancel, a fresh edit or a reset invalidates it. Cancel closes editing immediately and leaves the applied session intact, but explicitly reports the draft as *saving* until one strict IndexedDB write has completed; it reports saved only after that commit, or displays an actionable failure without claiming durability. Opening and cancelling an **untouched** displayed default template does not convert canonical `draft:null` into an authored draft; deliberately typing the same default does count as authorship. The existing serialized Plan writer and the independent draft/session separation remain authoritative; no additional persisted format or background subsystem is introduced. Real-browser and device acceptance remains a separate gate.

**BF-C6.2 — Previous-day convergence and evidence (2026-11-05).** A canonical previous-day Active Session is historical work regardless of whether it was active or suspended, and regardless of the device named by `runningOn`. Startup, ownership rehydration, the former Continue Here action, and backup/rollback restoration route it to a **Previous Day Needs Review** state, not a runnable or transferable timer. A covering canonical Saved Day, combined with that session's own durable acknowledgement, retires its redundant local recovery copy before the Review prompt. While historical Review remains open, the normal clock and timer-engine rollover adapter must not auto-save or close that previous day: the user decides when to save it. Otherwise the person may recover it into Review without starting the timer, leave it stored with a persistent **Review Previous Day** action, or deliberately discard a local-owned copy through the existing exclusive mutation owner and strict canonical deletion verification. A remotely owned historical copy is never offered destructive local discard. A changed canonical session invalidates an outstanding Review choice rather than applying a stale decision.

**Reminder reconciliation.** A Save Today warning captures only a strictly committed same-date session snapshot whose content revision matches the visible runtime. Following a canonical Saved Day write or completed backup reconciliation, the warning is checked afresh against the actual canonical Day, canonical session acknowledgement (if still present), and any retained uncovered divergent session. After verified coverage, it may be dismissed **without** changing `savedRevision` or falsely acknowledging another session; its old inline Review instruction is cleared only if that instruction has not been replaced by newer status feedback; missing evidence, local rescue-only current session, an unacknowledged current session, or failed storage reads retain the warning. The evidence is volatile in-memory notice context, not another stored state or merge authority.

**Safely extended evidence.** The shared `DailyRecordCodec.savedDayCoversSessionEvidence` predicate allows non-decreasing measured progress and exact-prefix pause events. A later focus end is additionally accepted only when the original start is unchanged, the finish is strictly later and actual recorded focus duration has increased. Partial Practice Pacer runs may continue only with the same task/target/plan metadata and an exact unit-duration prefix; runs are matched one-to-one, reserving exact complete-run matches before assigning partial continuations. Edited or missing starts, shorter duration, non-prefix practice, a changed target, unrecorded results, unacknowledged session work and unverified saved data remain conflicts requiring recovery or review. No global timestamps or cross-device numeric revision comparisons substitute for semantic proof.

## Across devices

Decisions (owner, 2026-10-18):

- The session names the device running it; only that device runs the timer. Another device shows "Running on another device" and edits notes and everything else freely; notes from it reach the running device without stopping its session.
- Suspend hands the session over: it uploads at once and the other device offers Continue here.
- Continue Here and Restore Session sit in Execute's status card and in the session strip above the Plan board, in one order: next step, Suspend, Finish, Reset last. Controls that cannot act are hidden, not disabled. Continue Here on a device whose copy still runs elsewhere asks first; the device taken over from stops at its next sync and keeps its unsynced progress for review.
- "Needs review" opens during a running session and leaves the session as it is.

How Continue Here shows its steps and errors: [status-indicator.md](status-indicator.md#continue-here).

**How sync treats it.** The session names the device running it (`runningOn`, the installation id), and only that device runs its timer. Another device keeps a copy it never runs and shows "Running on another device"; notes, Saved Days and everything else work there as usual. Ordinary reconciliation still uses the exact canonical Active Session fingerprint stored in the shared reconciliation baseline. The lightweight Drive ownership claim is a separate control-plane fact: while its newest applicable epoch names this device, an older checkpoint naming the previous owner cannot hand execution back.

Ownership metadata and study content are deliberately different reconciliation domains. The Active Session codec defines a semantic content projection containing the date, applied schedule and study evidence while excluding `runningOn`, status, session/content/save revision counters and persistence timestamps. Continue Here binds its ownership claim to a SHA-256 fingerprint of exactly that semantic content. A pure ownership transition therefore creates no false content conflict. If the old owner later publishes study evidence that differs from the handoff boundary, sync can distinguish one-sided continuation from genuine two-sided divergence; genuine divergence is kept for review rather than discarded.

A Saved Day and an Active Session use related revision numbers, but those numbers are **not cross-device ancestry identifiers**. Save Today records the current session content revision in the Saved Day and, on that same session lineage, advances `ActiveSession.snapshot.savedRevision` before persisting the session again. On a later launch, a previous-day Active Session is retired quietly only when its own `savedRevision >= contentRevision` and the canonical Saved Day for that date exists. Sync does not infer that one device's Saved Day covers another device's session merely because their numeric counters compare. If the remote side has a newer Saved Day and no Active Session, that explicit end-of-session state outranks the ordinary running-session hold rule; any genuinely divergent local session content is kept for review before the stale recovery row is retired.

## Moving a session

Active Session content and ownership are separate. Continue Here first flushes the independent Plan draft, then reads the newest verified Drive head **without running general sync**: it verifies the head manifest/commit and opens only the repository object containing the Active Session. If the local and verified-shared semantic content fingerprints differ, Continue Here checks the current owner's preceding ownership claim. When this device still holds exactly the semantic content that claim recorded at the prior handoff boundary, the newer Drive Active Session is a proven one-sided continuation and is advanced locally before ownership moves—without touching Plans, notes or Saved Days. If that causal proof is absent, both sides diverged, or the newer session carries attachment dependencies, Continue Here stops and schedules ordinary sync so reconciliation remains lossless.

If the content matches, Continue Here acquires a new monotonic Drive ownership epoch through the protected **v4** claim (v3 remains readable for earlier handoffs). The claim contains opaque session/owner tokens plus a SHA-256 fingerprint of the exact semantic session content observed at handoff; no schedule, progress, device id or date is stored in plaintext. Under the publication lease, Drive's head is re-listed and must still be the exact verified checkpoint that was observed before the claim is written. Only after the claim is durably read back does this device strictly save and read back the new local owner session; only then may its timer run. A failed local commit writes a newer compensating ownership claim when that rollback can be verified. If compensation itself cannot be verified, the handoff fails closed and the timer does not start; reloading/retrying resolves the durable claim rather than pretending ownership is known.

The newest applicable ownership epoch remains authoritative until a later verified epoch supersedes or explicitly releases it; it does not expire by time. An open old owner checks the lightweight claim about every 15 seconds, flushes its latest progress, freezes only its runtime clock, and forces Drive catch-up; canonical progress remains untouched so ordinary reconciliation can keep any divergence for review. Older claim files are compacted best-effort after a successful full checkpoint. Suspend and plan-apply still publish urgently through the normal shared checkpoint path.

## When this device loses the session

When a verified lightweight Drive claim shows that this device no longer owns its running Active Session, Study Director stops its local execution loop immediately and preserves the frozen timer/practice evidence. The local draft must commit through strict canonical IndexedDB storage and pass a matching strict read-back before claim-triggered sync starts. Failure, null result and emergency local-only rescue are **not** declared canonical; the page retains a persistent safety warning and retries through its existing 15-second claim watcher. A managed-recovery preflight still independently rejects unverified snapshots; it can incorporate later Session reflection edits without adding time spent frozen. If the claim returns to this device, the runtime resumes only when the frozen state was saved and the TimerEngine actually resumes. No guarantee of recovery exists when every browser storage surface is unavailable and the page is terminated; keep the page open and heed the warning. BF-1 originally advanced the lightweight ownership-claim protocol to v3; BF-1R3 subsequently added the v4 claim and correlated v2 local safety latch. The canonical Active Session schema is unchanged.

The visible/eligible Active Session claim watcher keeps its **15-second** cadence and the parallel remote claim/strict local session reads. A confirmed-offline browser avoids futile Drive claim reads; returning online or making a hidden tab visible can immediately perform a missed eligible check. Those event-driven wakes use the same single interval owner's 15-second attempt throttle and the check's existing in-flight guard. Explicit claim verification remains independent of the wake throttle so a failed frozen-session local write can still retry through the normal direct path. This is **open-app cooperative work**, not a closed-app OS background service, and remote handoff cannot be observed while truly offline.

## BF-1 corrective audit: invariants and recovery (2026-11-03)
**BF-C7.1 — date-first recovery and initial Plan Apply (source-corrected 2026-11-05).** When the persisted handoff-safety latch has been resolved, `continueSessionHere()` and `restoreSuspendedTodaySession()` re-read the canonical Active Session and classify its date before choosing a today-only restore or ownership path. Historical active/suspended sessions, whether locally or remotely owned, remain under Previous Day Needs Review; neither a timer nor an ownership transfer starts. A failed strict canonical read after safety resolution blocks restoration. Existing current-day remote ownership and suspended-session flows are preserved. Independently, the enabled initial Apply Draft action is now a valid deliberate first-Plan action without prior editing mode; it performs one strict draft commit before application, and edit-epoch and session-state guards prevent an older asynchronous action from changing a newer Plan. The default fallback remains unsaved until explicitly authored/applied. The 157-file fast suite and build gates passed ([CI](https://github.com/oneshubhamt/study-director/actions/runs/41980536922)); browser and physical cross-device verification remain outstanding. See [BF-C7.1 ledger](../backlog.md#bf-c71--plan-action-and-date-first-post-safety-routing).


A second, production-source audit found that the initial BF-1 changes did not yet satisfy every invariant. The follow-up fixes preserve the existing independent Plan/Active Session domains and make these rules explicit:

1. **Canonical selection is not a clock race between unrelated study dates.** Two different-date Active Sessions are independent work. On an automatic sync, this device keeps its own active session; the distinct incoming session is retained for review. Replaying an unchanged divergence does not enqueue another copy.
2. **Ownership evidence precedes apparent equality.** A verified newer Drive ownership epoch must be examined even when the local Active Session and the older checkpoint are byte-for-byte equal. A failed ownership-claim read is **unknown**, not verified absence; sync fails closed and retries rather than letting an old checkpoint transfer ownership back.
3. **The old runtime stops before a remote owner or verified ended state replaces it.** Reconciliation owns this quiescence along with its canonical selection and retained versions, rather than leaving the timer running under already-replaced control state.
4. **Ownership requires strict canonical IndexedDB persistence.** Acquisition, yield and restored/suspended-session critical writes use the same full-record read-back predicate. A localStorage recovery envelope is useful rescue evidence but cannot prove a successful ownership commit; equal revision numbers with different content do not pass.
5. **A failed acquisition is recoverable without speculative rollback.** A profile-scoped, content-free `sessionHandoffSafety` latch is committed before requesting the protected Drive claim. If the local record is exactly the proposed or observed previous session, compensation may restore the previous owner, then clear the latch. Unrelated canonical progress is never overwritten to force compensation. If the claim or rollback remains uncertain, the latch survives reload and prevents automatic session execution until Drive ownership and canonical local state are verified. The Execute/Plan status surfaces explain the blocked recovery and offer verification when possible.
6. **Plan draft persistence is a separate barrier.** Continue Here flushes any pending Plan draft, awaits the existing PlanData persistence chain and reads the canonical draft back before claiming ownership. Restoring or reconciling a session never uses the draft as schedule transport; importing Personal Data does not enter Plan edit mode while a canonical Active Session exists, including suspended/elsewhere states.
7. **Saved Day acknowledgement is lineage-local.** A numeric revision from another device is never independently proof of coverage. The saved session's own acknowledgement plus the canonical Saved Day retires a redundant previous-day recovery row; genuinely divergent unsaved evidence remains reviewable.

**Validation gate:** fast integration scenarios in `tests/integration/backup/sync-shared-base.mjs` cover cross-date isolation, repeated divergence, unreadable claims, ownership handoff and ended-session convergence. The acquisition/yield failure-injection scenarios in `tests/integration/app/session-claim-flush-safety.mjs` cover local-only writes, exact-read mismatches and compensation. Targeted Chromium journeys in `tests/browser/backup/session-plan-sync.mjs` and `tests/browser/app/session-draft-edit.mjs`, followed by actual iPad/iPhone/desktop confirmation, remain necessary before calling BF-1 certified.

## BF-1R3 durable ownership-claim recovery (2026-11-04)

**Owner-approved persistence exception:** Reuse the existing profile-scoped `sessionHandoffSafety` browser-storage key. Prior v3 claims and v1 local safety markers stay readable but cannot falsely satisfy a v2 claim correlation. No additional IndexedDB stores, OPFS entities, browser-storage keys, Active Session fields, backup units or parallel journals.

**Recovery protocol:** Confirm strict canonical IndexedDB state and the latest readable Drive claim. Where the v2 marker's UUID, observed owner, exact content and revisions match the newest claim, verify the current Drive Active Session independently. A previously accepted claim may be adopted with a **strict** local commit and exact canonical read-back; the claim's epoch is rechecked before execution. A verified higher-epoch compensation returns control only to the original owner. A checkpoint that advanced only unrelated data is harmless when the latest complete Active Session is exactly the same. Read failures, offline operation, lost mutation authority and uncertain compensation all preserve the marker; verification can be retried after reload or reconnection.

The conditional strict IndexedDB transaction reads the expected previous canonical session and replaces it only if exactly unchanged; a mismatch aborts without an emergency recovery envelope, so newer local study work cannot be overwritten.

## BF-C2 — Handoff compensation and superseded claims (2026-11-04)

Compensation after a failed Continue Here now restores the prior Active Session only through the repository's existing strict `expectedCanonical` IndexedDB compare-and-write. A canonical edit between read and write aborts; the claim is not released, the safety latch remains, and unshared progress is preserved.

For an interrupted v2 handoff, a different newer Drive owner can supersede the attempt only when its verified claim proves that it observed the exact handoff boundary, and the newest verified checkpoint names that owner. Its checkpoint may contain later work if this device's evidence stayed unchanged, the checkpoint is not older than the successor claim, and the new session does not require uncollected attachments. Both a never-adopted predecessor and an already-adopted local owner are conditionally updated to the exact verified remote-owner session, so the local canonical control state also converges. Neither case starts a local timer. The remote claim is rechecked before and after any conditional write. An interrupted latch cleanup can be retried idempotently. If study content, claimed owner, canonical local state or remote verification does not agree, recovery remains fenced and waits for normal reconciliation. No new persisted marker, key or schema was introduced.

Browser handoff and actual desktop/iPad/iPhone acceptance are still required.

## BF-C4 — Saved-evidence retirement without full-session hash equality (2026-11-04)

The last-shared Active Session fingerprint remains an SHA-256 of the **complete canonical session**; it is not relabelled as a semantic hash. A local session can acquire a new control revision, snapshot timestamp or durable save acknowledgement while retaining the same study evidence. The existing `sessionFullyAcknowledged` predicate and production `savedDayCoversSessionEvidence(..., {allowAdvances:true})` now provide an independent, positive proof for retiring an old-date session when a verified successor checkpoint has saved that date, or for accepting an already-ended session from a verified descendant of its shared ancestor. Without full ancestor identity **or** both local save acknowledgement and actual Saved Day coverage, the app preserves the unproven work for review. A Saved Day tombstone cannot establish coverage.

No owner is inferred from cross-device scalar revisions, no claim identity or protected Drive ownership format changed, and the existing positive claim epoch always takes precedence. A running old-owner timer is still yielded before replacing its session; any newly captured evidence after that yield is retained for review. The former `daySavedSinceBase` function was removed: metadata-only change to an existing Day's full SHA was not proof of a new save. Existing `sessionFingerprint` and `dayFingerprint` remain unchanged for their baseline writers and strict proven ancestry.

**QA contract:** two-device cases now cover unchanged semantic content with changed full metadata and acknowledged Saved Day, actual unsaved divergence, unacknowledged content, deleted Day, repeat sync and ended same-day checkpoint. Production coverage checks independently reject reduced/contradictory work and accept demonstrable later progress. Browser/device execution remains outstanding. An unprovable semantic ancestor cannot be reconstructed from an existing full-record hash; the remaining false-review corner requires an explicitly approved versioned local semantic baseline and is deliberately not guessed.

## BF-C4.1 — Semantic study ancestry with unchanged execution ownership (2026-11-04)

The existing last-shared canonical full-session SHA-256 remains unchanged. A new, independent hash of `ActiveSessionCodec.contentValue` is stored in the local `ReconciliationBase.v5` header, alongside the old hash; legacy bases without it remain unknown. This distinguishes actual study progress from session control changes (owner token, running status, control revision, save timestamps), so a verifiably unedited study branch can follow one-sided later progress without a meaningless review.

**Crucial safety separation:** A semantic match is **not** proof that locally unsaved study has already been committed to a Saved Day. Automatic old-day session retirement still requires a canonical covering Saved Day and either the exact unchanged *full* ancestor or a durable acknowledgement `savedRevision >= contentRevision`. The protected Drive ownership claim, monotonic epoch and verified observed-content fingerprint remain the only execution-owner causal authority; semantic ancestry cannot silently reassign the running timer. Genuine late study, timer capture after yielding, and ambiguous claims remain reviewable/fenced.

The upgrade introduces no new Active Session fields or saved-record schemas, does not rewrite old fingerprints, and relies on the existing strict baseline update contract. ## BF-C7.3 — Save Today notice-only canonical convergence (2026-11-05)

Save Today reminders are **notifications about outstanding evidence**, not durable save receipts. A local dirty revision counter may remain after another device has independently committed equivalent or advancing study content. `savedRecordExistsForDate` and `revalidateSaveReminderAfterCanonicalConvergence` therefore check the **actual canonical Saved Day** against the current canonical session (when present), the exact originally warned-about session/live evidence (if captured), the current runtime snapshot (where available) and any unresolved divergent retained session. `DailyRecordCodec.savedDayCoversSessionEvidence` is the shared evidence predicate, followed by strict canonical Saved Day verification; the current canonical session and runtime are reread where relevant to avoid stale asynchronous clearance.

An unreadable record, rescue-only canonical source, uncovered retained alternative, changed live evidence or otherwise unknown coverage **keeps** the reminder. If the original canonical-session capture failed or lagged, a fresh live schedule/snapshot can serve as **in-memory notice evidence**, but is never relabeled a committed Active Session. Proven convergence may retire only the obsolete reminder and its exact matching inline instruction; it does **not** write `savedRevision`, automatically save new data, clear a distinct new manual feedback event, or change ownership. A per-reminder generation fence protects a second same-day warning from an older verification completing late.
