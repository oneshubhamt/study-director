# Experimental native platform (Tauri)

Scope: branch `tauri-spike` only. This programme experiments with the JavaScript F33 application, without changing main, ts-exp, deployment, release identity, existing workflows or production credentials. It does not imply production support.

The normal build generates dist/development and dist/deployment; the native target must consume reproducibly generated assets rather than editing dist. Keep the existing web pipeline unchanged.

## Authority and platform boundary

Use the host composition root in source/app.html and the existing frozen internal-module ports. Select the platform once before composing capabilities. The browser implementation is still a first-class client. Do not scatter runtime detection or expose a general-purpose filesystem/SQL/network bridge. A native application identifier and data directory must be stable but isolated from production browser storage and any future production native identity.

## Platform dependency census and build decisions

The source inspection covers the host, all core modules, Drive, service worker, authored portable workers and the rich-text/editor boundary, plus the authored Insights, Guide and skins. This is an architectural/lexical census with direct inspection of the important composition and persistence paths, not proof of runtime availability or exhaustive transitive vendor behavior.

- Browser database: persistence, repositories, app-meta, host profile scope and storage census; IndexedDB, IDBKeyRange, local/sessionStorage and storage events. Profile removal also deletes scoped databases and directories. Recovery journals, unsupported-data protection and local change clocks must remain authoritative.
- Files: asset-storage, attachment-ingest, attachments, exports, device-backup, device-folder-storage and portable file/attachment workers use directory/file handles, writable streams, synchronous access handles, object URLs, Web Locks and verified hashes. Rich-text image preparation depends on worker messaging, OffscreenCanvas and createImageBitmap. User export/import pickers and PDF/audio/image presentation are separate from managed repository transport.
- Coordination and lifecycle: ownership, mutation-coordinator, startup, app host, save lanes, session/timer, backup-provider and repository-background. Web Locks, BroadcastChannel, storage events, pagehide, visibilitychange, pageshow, beforeunload, online/offline and timers; use the same ownership and settlement gates.
- Network/security: Drive GIS script, XMLHttpRequest uploads, fetch and bearer state; Guide fetches packaged legal resources; Trusted Types, CSP, secure-context Web Crypto and Blob URLs. Retain the existing narrow trust boundary. The browser Drive provider must not load or authenticate on native until a native transport is ready.
- Other OS/presentation: native-capabilities is currently a browser-capability controller (installation, persistence status, wake, badges), not Rust IPC; SystemNotifications in the host, audio-engine, editor clipboard and links, fullscreen and matchMedia. Preserve presentation behavior, expose actual platform availability, and never use WebView user-agent as native authority.
- Build: renderBuild derives both web targets, validates module/asset inventory, fingerprints content, creates a PWA asset identity and computes deployment CSP. The native asset target should use the same render pipeline, explicit build-selected platform capabilities, no production OAuth bundle, no service worker or web install manifest, no Firebase configuration, and its own page asset identity. Do not copy a production deployment as the native app.
- Windows origin: deliberately choose HTTPS custom protocol and a separate experimental application identifier before the first install. Changing useHttpsScheme later changes the WebView's storage origin ([Tauri configuration reference](https://v2.tauri.app/reference/config/#usehttpsscheme)). Use packaged assets at that origin for the real durability witness, not a localhost development server. No production app data is to be used.

The existing baseline CI and [documentation-only branch checkpoint CI](https://github.com/oneshubhamt/study-director/actions/runs/45320892852) both succeeded. The runtime source and build were identical between them. Independent exact-revision hosted baseline reproduction passed; the dedicated Windows CI runner provides actual native build and packaged WebView2 runtime evidence. P0 is VERIFIED — TARGETED.

## Native frontend staging

`node build/stage-tauri.mjs` renders a third, explicit target under `dist/tauri` from the same canonical source, module manifest, workers and static assets. It is not a Firebase or PWA deployment. Native assets carry a separate page asset identity; the host composes the build-selected platform once, does not grant the PWA lifecycle coordinator a service-worker capability, and has no browser Google Drive plugin. Web targets keep their manifest, service worker and OAuth provider. Staging validates shared asset hashes and inventory and does not write either web target. The native target is local-only; it is not an authorized test against the owner's library. The initial Rust shell is intentionally local-only and unprivileged. The stable experimental identifier is `app.studydirector.taurispike`, the Windows origin is `https://tauri.localhost`, and the Windows WebView data directory is the application's local data directory plus `webview`. No global Tauri API, plugin or custom IPC command is exposed. The Rust-created window rejects non-packaged navigations and new windows; external-browser integration and PDF/new-window behavior still need native qualification. The early platform composition is immutable and rejects unknown targets before installing platform-specific listeners. PWA installation capture, browser-managed folder registration, browser system notifications and popup PDF handoff are not admitted by the native shell; inline PDF preview remains the shared path. Drive and Device Folder are explicitly unavailable until their native adapters land, including first-start, profile and recovery guidance. Portable backup/import remains on the shared local path; the shell does not claim native update availability or fabricate browser storage protection. The shell uses the native-only generated icon and does not bundle an installer. See [src-tauri/README.md](../../src-tauri/README.md) for the packaged-origin build and acceptance gates. The branch-only Windows QA workflow has read-only permissions, uses disposable runner data, and creates short-retention smoke-tested experimental artifacts without publishing releases. The test runner uses a temporary executable-specific machine-policy override (the documented elevated-host WebView2 mechanism); the product remains unmodified. Each run builds its own commit with the authentic committed dependency lock before executing the packaged-runtime witness.

## Critical risks and qualification gates

1. **OAuth interoperability**: the web grant is drive.file and repository discovery depends on private appProperties. Before native creation/publication, confirm an installed-app OAuth client in the appropriate Google Cloud project and prove visibility of existing app-created files and appProperties with the narrow grant. Do not silently broaden permission or create a duplicate library when discovery fails. Test wrong account, rejected consent, callback state mismatch, refresh expiry/revocation and no-token leakage. Owner approval is required for external OAuth configuration. Distinguish local disconnect from account-wide revocation.
2. **Local durability**: use disposable profiles/fixtures only. Test failed/unknown storage reads, quota, write interruption, actual process kill, close/reopen, OS restart, attachment mismatch, unsupported formats, and recovery. Stable WebView origin/data directory is part of persistence identity. Never claim WebView storage protection from Chromium branding alone.
3. **Repository integrity**: fail closed on missing/unverified reads, interrupted staging, publication or cleanup; protect current and safety checkpoints, immutable hashes, references, ancestry, deletion ledgers and conflict decisions. Test retries, overlapping publication/maintenance, partial inventories, interrupted restore and stale leases against both transports.
4. **Lifecycle/security**: validate IPC caller and capability scope, restrict native paths and URLs, avoid broad shell/filesystem permissions, enforce CSP and signed update trust, hold editor and mutation reservations across verified update/close preparation. Test timeout, cancellation, stale callbacks, suspension and external navigation.
5. **Native migration**: one canonical owner at each point; verify exact representation, transaction and read-back before a durable migration marker switches authority. Preserve old data until verification and recovery gates succeed. Test kill and rollback at every step, unknown schema, SQLite corruption and attachment corruption. Retire the superseded native adapter only after proof. Web IDB/OPFS remain.
6. **Cross-platform acceptance**: isolated test library, PWA publishes → independently authorized native discovers and reconciles → native edits/publishes → PWA reconciles, including conflicting edits, deletions, restore, attachments, safety versions, cleanup and session handoff. Do not test against the owner's live library.

## Sequence and closure gates

The complete [native programme roadmap](../native/PROGRAMME.md) defines scope, dependencies, outcome-specific negative witnesses and full certification. [AGENTS.md](../../AGENTS.md#native-programme-on-tauri-spike) governs execution; the [compact register](../../TAURI-EXECUTION.md) owns current evidence and closure state. Product contracts remain here. Source-only reasoning, real packaged CI, authorized transport tests and physical-device tests are different evidence classes. No roadmap entry authorizes external configuration, deployment or use of the owner's data.

Native Drive is an optional, configured-only composition of the same provider with a separate native connection owner. The Rust application permission grants exactly `native_drive` to the main packaged window; no generic HTTP/OS/filesystem bridge. A stable local-profile native session is retired on navigation without deleting the OS refresh grant. Its independent transport validates fixed Google endpoints and repository operation grammar, private folder and repository metadata, original authorization generation, bounded streams and server-issued resumable sessions (returned as opaque handles); it admits mutations only after existing matching commit/checkpoint and object bytes and folder/deletion status are verified. The shared provider still owns canonical publication/reconciliation/retention and local profile decisions. Credentials are never put into WebView storage or the PWA build. Configured Google-account interoperability remains a separate open acceptance gate.
