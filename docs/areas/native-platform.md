# Experimental native platform (Tauri)

Scope: branch `tauri-spike` only. This programme experiments with the JavaScript F33 application, without changing main, ts-exp, deployment, release identity, workflow configuration or production credentials. It does not imply production support.

## Baseline and evidence

Baseline: `d69f2053629a7e24d106a969f0d69eac65b4996b` (main, SDVB75F33), source tree `7ae2c068f2964f8e1eac58536e885ab14532eff4`. The existing [Repository checks run](https://github.com/oneshubhamt/study-director/actions/runs/45050852078) on this exact SHA passed fast (unit/integration/architecture), PWA deployment contract, source build, generated build verification and generated syntax. This is existing CI evidence, not an independently reproduced local run, a browser-suite run or a native acceptance result. The normal build generates dist/development and dist/deployment; the native target must consume reproducibly generated assets rather than editing dist. Keep the existing web pipeline unchanged.

## Authority and platform boundary

Use the host composition root in source/app.html and the existing frozen internal-module ports. Select the platform once before composing capabilities. The browser implementation is still a first-class client. Do not scatter runtime detection or expose a general-purpose filesystem/SQL/network bridge. A native application identifier and data directory must be stable but isolated from production browser storage and any future production native identity.

In particular the current format ledger has backup metadata 26, manifest 11, repository commit 1, protected manifest 3, ownership claim 4, DailyRecord 16, Note 3, ActiveSession 11, SessionSnapshot 6, PendingReview 2 and personal data 2. Device Folder scope 2, publication and maintenance coordination markers, Drive appProperties and profile/deletion identities must retain their exact meanings. The attachment operational ledger currently specifies version 2 with storage 'opfs'; distinguish native local physical location from the shared canonical attachment identity and serialization, with fixtures before any change. Unknown/newer data stays untouched and blocks destructive convergence where necessary.

## Critical risks and qualification gates

1. **OAuth interoperability**: the web grant is drive.file and repository discovery depends on private appProperties. Before native creation/publication, confirm an installed-app OAuth client in the appropriate Google Cloud project and prove visibility of existing app-created files and appProperties with the narrow grant. Do not silently broaden permission or create a duplicate library when discovery fails. Test wrong account, rejected consent, callback state mismatch, refresh expiry/revocation and no-token leakage. Owner approval is required for external OAuth configuration. Distinguish local disconnect from account-wide revocation.
2. **Local durability**: use disposable profiles/fixtures only. Test failed/unknown storage reads, quota, write interruption, actual process kill, close/reopen, OS restart, attachment mismatch, unsupported formats, and recovery. Stable WebView origin/data directory is part of persistence identity. Never claim WebView storage protection from Chromium branding alone.
3. **Repository integrity**: fail closed on missing/unverified reads, interrupted staging, publication or cleanup; protect current and safety checkpoints, immutable hashes, references, ancestry, deletion ledgers and conflict decisions. Test retries, overlapping publication/maintenance, partial inventories, interrupted restore and stale leases against both transports.
4. **Lifecycle/security**: validate IPC caller and capability scope, restrict native paths and URLs, avoid broad shell/filesystem permissions, enforce CSP and signed update trust, hold editor and mutation reservations across verified update/close preparation. Test timeout, cancellation, stale callbacks, suspension and external navigation.
5. **Native migration**: one canonical owner at each point; verify exact representation, transaction and read-back before a durable migration marker switches authority. Preserve old data until verification and recovery gates succeed. Test kill and rollback at every step, unknown schema, SQLite corruption and attachment corruption. Retire the superseded native adapter only after proof. Web IDB/OPFS remain.
6. **Cross-platform acceptance**: isolated test library, PWA publishes → independently authorized native discovers and reconciles → native edits/publishes → PWA reconciles, including conflicting edits, deletions, restore, attachments, safety versions, cleanup and session handoff. Do not test against the owner's live library.

## Sequence and closure gates

- Phase 0: finish source/platform inventory and independently reproduce baseline where possible; confirm build asset/native origin and qualification environment. Existing CI is the baseline evidence currently available.
- Phase 1 A–F: shell/platform boundary; native Drive auth; Device Folder transport; useful OS capabilities; separate safe signed updater; Windows packaging/security. Keep IndexedDB/OPFS as the native local owner. G: comprehensive real Windows qualification plus shared-source PWA regression.
- Phase 2 A–H: Rust/SQLite design; bounded shadow verification; domain migration; native attachments; repository engine; sync/background engine; cross-platform qualification (investigate Android); retirement of native IDB/OPFS authority. I: full fault-injection and architecture qualification.
- No phase is complete on source inspection, CI or mocks alone. Native Windows behavior, real OAuth, interoperability, installer/updater and restart/power-loss behavior require the corresponding environment and evidence. Keep unfinished outcomes in backlog.

No runtime implementation is authorized by this document alone; each pass needs its own bounded objectives, invariant/failure-path review and targeted checks before closure.
