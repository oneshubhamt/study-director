# Backup and sync

Automatic backups to the Device Folder and Google Drive, Version History and restore, standalone backup files, and sync between devices through Drive. Device Folder and Google Drive are independent destinations served by one engine. They share the repository format (immutable versions, content-addressed objects, commit markers and coordination files) and the same safety rules, but each destination owns its own history and transport state.

## Shape

- **Repository core** (`managed-repository.js`, existing). Checkpoint capture and preparation, the publication protocol, verified reads, retention selection, cleanup planning and the integrity scrub. Format-level code only.
- **Engine** (`backup-provider.js`). Owns every operation on a backup location, the same way for every location:
  - Back up: lock, read the repository state, publish, then bookkeeping.
  - Version History.
  - Open a version for restore, in four scopes: whole version, add what's missing, one note, and attachments or Saved Days.
  - Maintenance: retention cleanup and object garbage collection.
  - Integrity scrub.
  - Automatic scheduling and retries.
  - The protected safety backup before a restore.
  - Foreground and background coordination, and status.
- **Storage adapters**. Each one only knows how to reach its storage:
  - `list(kind)`, `download(item)`, `upload(file)` (verified) and `delete(item)` for checkpoints, commits and objects.
  - `download(item,{offset,length})` reads a range of at most 1 MB for the integrity scrub and returns `{blob,totalBytes,version}`. The version is the one the listing gave (Drive's revision, the Device Folder file's modified time), so a file that changes between ranges restarts verification.
  - The lock files, with the same names and formats as today, so devices on different app versions still coordinate.
  - Connection state, permission and authorization.
  - Device Folder: a local directory handle (`device-folder-storage.js`). A thin controller (`device-backup.js`) keeps the chosen folder, its permission, remembering it across launches and its status row.
  - Drive: the Drive API (`drive.js`).

**Ownership.** The backup provider is the sole owner of checkpoint/commit history-list normalization, the comparison of planned versus current cleanup identities, and the publication read-back lease/checksum lifecycle. Both ordinary Version History discovery and destructive cleanup use the same identity parsing; only cleanup requests fresh content digests. Immediately before deletion, the engine repeats the manifest/commit digest check under its exclusive maintenance lease, treating any changed or unreadable identity as a reason to defer rather than delete. Manifest and commit **provenance** validation remains separate after the shared byte verification; format validation, object retention and canonical capture still belong to `managed-repository.js`. Storage adapters produce physical listing, transport and checksum evidence but do not decide which backup version is safe to retain or remove.

## Rules the engine applies once

- **Needs a backup.** Each location records the change time its last committed backup captured. It needs a backup when the change clock has moved past that. The clock is the mutation epoch written inside every save's transaction, and it only moves forward.
- **Automatic timing.** One cadence for every location (`automaticQuietMs`, `automaticUrgentMs` and `automaticExpiryLeadMs` in `repository-policy.js`): within 20 minutes of the first change a location does not hold, within three seconds of a key moment (finishing the day, all blocks resolved, saving a day to Library), and five minutes before a sign-in that expires runs out. The first waiting change owns the deadline: later changes and other wake-ups never move it, and changes made during a backup wait a full cadence from its end. Changes found on start or on reconnect (not seen being made) go at once, but only while local data is present, so an emptied browser never becomes a location's newest version. Waiting changes also go out at once when the app goes to the background (a phone may close it there), and before an update applies (the update waits up to a minute for them).
- **When a location backs up on its own.** The Device Folder from when it is chosen: an empty folder gets a first backup at once; a folder that already holds backups is left as it is until this device's next change. Drive whenever it is signed in, because it syncs (below).
- **Drive sign-in.** Google ends a sign-in after about an hour. The sign-in is kept for the rest of that hour across reloads and reopening (`studyDirector.driveSession.v1` in localStorage, shared by the device's tabs) and forgotten on expiry, disconnect or a rejected token. No refresh token is requested. Changes made while signed out go up on the next sign-in. When a sign-in ends, a person who uses Drive gets one toast with Reconnect, which they can dismiss; nobody else is told anything.
  - **Security trade-off (reviewed October 2026).** The access token is a bearer credential in origin-local `localStorage` for its remaining lifetime; a script that executes in this origin or an extension with relevant access may read it. Same-origin policy, CSP and Trusted Types reduce some attack routes but do **not** make localStorage a secret vault. The OAuth grant requests only `drive.file`, not unrestricted Drive access, and no refresh token is stored. Keeping the credential across reloads avoids frequent sign-in prompts but increases exposure versus memory-only storage. Changing to memory-only authorization is a separate product and security decision.
- **Independent destinations.** A backup is published from this device's verified canonical local state independently to each enabled location. Drive never waits for Device Folder to create a version, Device Folder never downloads a Drive checkpoint, and neither provider backfills the other's history. Expensive logical capture/preparation work may be reused locally, but provider publication and checkpoint identity remain independent.
- **Same data, no unnecessary write.** Each location compares the canonical state it is about to publish with what that location already holds. If its newest version already represents the same logical state, publication is unchanged rather than manufacturing an echo version. Taking in another device's Drive changes may therefore produce a Device Folder version without causing Drive to upload the same state again.
- **Unified Version History UI, independent repositories.** The host reads each connected location and presents one logical history. Equivalent logical versions may be deduplicated in the UI even though their checkpoint ids are independent; a version held only in one location says where it is. Restore reads from the selected verified source, and each location keeps and cleans its own repository. A note's earlier versions are gathered the same way, with logical coverage used to avoid duplicate entries rather than shared checkpoint identity.
- **What the list reads.** Each version's summary (date, counts, tier, device, format, missing attachments) comes from the listing: the Device Folder reads it from the version's manifest, Drive from its properties (the format is `sdHistoryFormat`, and a file without it is older than manifest 8; the number of attachments the version is missing is `sdHistoryAttachmentsMissing`, read as none when absent). A version missing attachments, in any location that holds a copy of it, does not offer **Replace current data**; Combine and Add only what's missing remain, and the restore itself still refuses an exact replacement it cannot complete. With a password put off at start, opening Version History asks for it first; a Device Folder version still waiting for it is listed as "Locked" without counts, and a copy that can be read is shown instead where one exists.
- **A version this build cannot read.** Its file's content fails the build's checks: another format (a newer Study Director, or an unreleased one), or damage (`repositoryUnreadable`, set only when the bytes were read; a failed read or a password wait never counts). Version History lists it on its own and muted, "Can’t be read by this app", with Restore… disabled and Remove… in red (a confirmation; `removeRepositoryProviderVersion`, which removes only this device's safety version or a version a fresh scan confirms unreadable). Cleanup keeps it and goes on around it: retention still removes the readable versions it drops and unfinished leftovers, but no shared object is removed while it exists, since nothing says which ones it uses; this waits for a Remove, not a timer. "Format cleanup" counts it (`unreadableVersions`), so it never reads ready while one exists. Any other failure (a listing it cannot complete, a version it cannot identify) still stops all deletion. When it is Drive's newest version, sync reads it once and then waits: the status says "Needs app update", one notice offers Check for update, nothing is retried and nothing is uploaded over it (a device that can read it would take such an upload as newer than its own changes). Removing it, or an update, lets sync carry on.
- **Every restore names its version.** Version History, sync, recovery at start and add-what's-missing after a clear all pass the version; the engine refuses a restore without one (add-what's-missing finds its own). No location has a picker of its own.
- **One reminder.** The 7-day backup reminder counts every backup (file, Device Folder, Drive). It stays away while an automatic backup can run, and while some backup already holds the latest changes.
- **Incremental in both directions.** A backup uploads only objects the location lacks. A restore reads only what the chosen scope needs and the device does not already have:
  - attachments with a matching checksum come from local storage;
  - a one-note restore reads only that note's objects;
  - every byte used is checked against the version's verified manifest.
- **Integrity evidence and reuse.** Canonical attachment metadata contains the expected plaintext SHA-256. OPFS ingest checks written bytes, ordinary attachment reads stay fast (metadata/existence/size), and a **new** managed-repository attachment object hashes the local plaintext before it can be published, including when backup encryption is enabled. Restore verifies local candidate bytes and downloaded attachment plaintext against the signed checkpoint descriptors; bad bytes are rejected, not accepted as recovered. An unchanged content-addressed object may instead be reused from previously verified, currently listed repository history without re-hashing its local copy or re-downloading its remote bytes on every publication. A new manifest/commit receipt therefore proves its own publication and references **previously** verified reused objects; it does **not** assert that every historical byte was freshly rechecked at that moment. Bounded recurring/on-demand integrity scrub checks remote object content (Device Folder) or the storage provider's own current SHA-256 (Drive), quarantines known corrupt objects and attempts safe republishing from canonical local data. Quarantined objects cannot be reused or restored; a repair must produce a newly verified checkpoint rather than rewrite an immutable identity. Ordinary reads, incremental publication and unrelated providers are not made to download/hash entire attachment libraries. Device Folder uses timestamp/size digest caching for ordinary listing only: destructive cleanup refreshes manifest and commit digests, and a selected restore re-reads and hashes both files before mutation. A missed or unavailable scrub is not represented as fresh all-object verification.
- **Retention.** 15 ordinary versions: Latest, six Daily, four Weekly and four Monthly, all chosen from periods that have a backup. Weeklies start below the oldest Daily's week and Monthlies below the oldest Weekly's month, so the history reaches about four to five months back. Leftover slots go to the remaining days, widest time gap first. On top of those, up to 10 Hourly versions from the 24 hours before Latest: one per local hour, only where the notes changed (each version records a fingerprint of its notes, `retention.notesFingerprint`; on Drive it is also the `sdHistoryNotes` property). On top of those, each device keeps its newest protected safety version for seven days (`protectedLimit` is per device, keyed by the version's `installationId`), so a restore on one device never pushes out another device's. The Device Folder and Drive use the same rules.
- **Safety.** Every restore makes a protected safety version first and rolls back locally if anything fails. A device with no study data (no Saved Days, notes, session, plans, attachments or open kept versions) has nothing to protect, so it uploads no safety version; just before applying, the restore checks again that the device is still empty and unchanged, and stops if not. A read that fails counts as not empty. The local rollback journal still guards the apply. Any local change after the safety version stops the restore before it applies anything, so while a restore, combine or sync runs, a running timer's once-a-minute snapshot waits and is written on the first tick after it (leaving the page still saves the session at once); before that, a snapshot landing during the safety upload made the restore start again with a second safety upload.
- **A restore reaches every device.** While Drive is connected, restoring any version (from Version History or a file) is uploaded to Drive at the next upload, and the other devices take it in at their next sync. The restore choices and the outcome say so.

## Managed repositories

Google Drive and Device Folder use the same managed-repository model:

- immutable logical objects;
- immutable checkpoints/commits;
- integrity verification before a checkpoint is accepted;
- verified history;
- retention and object garbage collection;
- incremental logical-unit preparation;
- bounded concurrent reads where appropriate;
- cancellation and foreground/background coordination.

The providers are intentionally not collapsed into one transport implementation because Drive authorization/remote consistency and File System Access permission/handle semantics differ materially. A shared UI may deduplicate logically equivalent versions from the independent repositories, but shared presentation never creates a storage dependency between them.

Drive is the only shared synchronization repository. Its normal convergence lane is pull/inspect newest head → reconcile into canonical local state → verify the committed logical units → publish the resulting canonical state. Device Folder independently receives that resulting local state when enabled. Repository retention, orphan cleanup, integrity scans and garbage collection are secondary housekeeping; their backlog does not gate healthy publication. Cleanup performs history verification, retention planning and object inventory without a maintenance exclusion. It acquires the maintenance lease only for a final metadata revalidation plus the bounded destructive unit; if the repository changed meanwhile, it releases the lease without deleting and replans later. Only an already-active destructive unit may therefore briefly hold a foreground publication until that unit yields or its bounded marker is safely reaped.

## Restore and Combine

Restore/Bring-in first verifies the selected checkpoint and reconstructs a verified portable snapshot. Destructive local replacement is protected by recovery journaling and a Before-restore checkpoint where required.

Combine/reconciliation handles Saved Days, Notes, Active Session and attachments through explicit domain rules. Reconciliation ancestry is incremental and provider history is scoped to the repository being inspected. Combine verification is receipt-driven and domain-scoped: Saved Days, Notes, attachments, personal data, Pending Reviews, deletion ledgers and Active Session report/verify the canonical units actually committed. Exact Replace retains complete-membership verification.

A sync through Drive never asks. Where both sides changed the same thing it shows the newer and keeps the other as a `PendingReview` record ("Kept for review", below); a note changed in different paragraphs is joined by Smart merge. The records travel in every version and merge by id, a resolved one winning. `reviewKeptVersions` (backup runtime) is the review: choices, then note texts in `reconciliation-ui.js` (`purpose: 'kept'`), applied through the same write paths as Combine inside one exclusive operation, skipping anything that changed while the person chose. A Library clear leaves kept versions as they are; their review still works for notes that are gone ("Keep for later" or discard).

Note reconciliation is format-aware and settles a difference by itself only when nothing on this device can be lost. The reconciliation base (header v5, day rows v2) is what this device last shared through Drive: each note's title and text, one fingerprint per Saved Day (rows `reconciliationBaseDays:YYYY-MM`), one of the Active Session and one of plans and settings. Only Drive moves it ("Shared base", below); it is the ancestor when a Device Folder or Drive version descends from it, and Saved Days and the session then merge three-way too. Plans and settings changed on one side only since then are taken from that side without asking. Combine takes a side's title or text when the other side still holds the shared one; applies a deletion, or keeps one, when the side that kept the note has not changed it since, or the deleting side holds that very copy in Recently deleted. Everything else is the person's: text in the review (keep this device's note, use the backup's, Smart merge, Append additions, or edit; "All remaining" settles every note not yet applied with one choice), deletions and titles in "Different versions found" (this device's state preselected). A note deleted by a deletion record moves to Recently deleted, with this device's copy when the person chose the deletion over local changes. Replace makes this device match the backup: a note whose text it changes takes the backup's copy when this device has not changed it since the handoff and opens in the review otherwise, starting from the backup's copy; a note the backup deleted moves to Recently deleted; and what this device has that the backup neither has nor deleted (notes, Saved Days, attachments, saved plans) is kept or removed by one question, "Keep them" by default. Removed notes go to Recently deleted and removed Saved Days are recorded as deleted. Recently deleted, the deletion records of both sides, and every attachment kept data uses stay. Restoring one note from an earlier version always opens the comparison. Historical rich-text portability is handled through explicit codecs rather than by exposing internal editor state as the durable format.

A deletion travels to other copies only as a deletion record (Saved Days, Notes, attachments); absence never means deletion. Each ledger keeps its newest records within its limit (`maxImportRecords`, `maxNotes` and 50,000 respectively), so it stays bounded without ever dropping a recent deletion: only once a ledger is full do its oldest records go. Listing applies that rule, so a full ledger never stops a backup or an integrity check; data maintenance removes the same records from storage, so pruning never changes what a backup or restore reads; and a restore verifies the ledger it stored. Backup import and the restore journal still reject a ledger over its limit. A dropped record matters only when a backup older than that many later deletions is combined, which could bring the oldest deleted items back.

## Retention

Device Folder and Drive share the same retention policy (`selectRepositoryRetention`): 15 ordinary recovery points, up to 10 Hourly versions from the last 24 hours, plus, for each device, its newest unexpired protected safety point (kept for 7 days). Safety points are extra temporary copies, as confirmed by the user; they do not displace an ordinary slot.

| Tier | Slots | Selection |
| --- | ---: | --- |
| Latest | 1 | Newest ordinary committed checkpoint |
| Daily | 6 | Newest checkpoint of each of the six most recent earlier days that have one |
| Weekly | 4 | Newest checkpoint of each of the four most recent Monday-based weeks that have one, counting only weeks wholly older than the oldest Daily's week |
| Monthly | 4 | Newest checkpoint of each of the four most recent calendar months that have one, counting only months wholly older than the oldest Weekly's month |
| Saved | the rest | Slots the tiers cannot use go to the newest checkpoint of the remaining days, widest gap in time first, newer on a tie |
| Hourly | up to 10 extra | Walking back over the 24 hours before Latest, the newest checkpoint of each earlier local hour (by the UTC offset captured with it) whose notes differ from the version kept after it. Versions that changed no note are not kept, so Version History is not crowded. Checkpoints without a notes fingerprint (written before it existed) count as changed |
| Protected safety | 1 extra per device | Each device's newest unexpired Before restore / combine / clear-library checkpoint, by the device that made it |

No Weekly shares a week with a Daily and no Monthly a month with a Weekly, so with a backup every day the Weeklies fall one to five weeks back, a week apart, and the Monthlies about a month apart beyond them, reaching four to five months back. Periods without a checkpoint are skipped rather than counted, so gaps of any length (inside a week, between weeks or months, or a break of several months) never empty a tier: after a break the history from before it stays, and graduates from Daily to Weekly to Monthly as new checkpoints arrive. Retention keeps one checkpoint per day, the newest, and keeps every day it can up to 15, so a new checkpoint replaces at most one version and the history is never lost wholesale. The latest day can be any weekday. Periods use the local calendar recorded at capture, so changing the evaluator's timezone does not reinterpret history.

A single note can be restored from the open note's ⋯ menu (Earlier versions…). It reads the connected backup locations (the Device Folder first; Drive skips versions it already read) and runs the same verified Combine limited to that note: the two texts are always shown side by side, nothing else changes, the restored text is saved as a new edit, and the version does not become the shared base for later combines. A version without the note, with the same text, or a review that keeps the current text changes nothing and makes no safety backup. It reads only the backup objects that hold that note and the images its text uses, each verified against the version's verified manifest, so a Drive restore downloads a few small files rather than the whole version; such a read can never be used to combine or replace everything. Because it never touches today's session, it is available during an active study session: the timer display pauses only while the change is saved, and that time counts as study time rather than an inactive gap.

Retention selects recovery points; it cannot enforce an instantaneous physical file limit. Publication first commits and verifies a new immutable version, then maintenance safely removes obsolete versions. A blocked, interrupted or failed cleanup can therefore leave more than 15 ordinary manifest/commit pairs temporarily. Each version has a manifest and a commit marker; shared objects are separate files and are not counted as versions. Version History projects retained points while physical cleanup catches up.

Drive history inventory now reads all pages, independently of the retention slot count. Pages remain bounded to 1,000 descriptors and history verification to eight concurrent reads. Each verified obsolete manifest is reduced to a compact retention/provenance proof; full object references are loaded only for the selected points. The existing full-body cache remains limited to 64 entries. Compact proofs are scoped to the current repository and exact listed immutable file identity/version/digest. They are reused on ordinary retry, discarded on changed identity or repository, and pruned when physical history changes or cleanup completes. They are in-memory acceleration; durable pending intent still owns wake-up after reload.

The same attempt validates every manifest/commit pair before authorizing deletion. Unknown history, an explicitly incomplete Drive search, repeated pagination tokens, or lost exclusion cannot produce a clean result or authorize reclamation. A version whose content this build cannot read is known rather than unknown: retention still runs around it, object GC waits until it is removed (Version History offers Remove), and no timed retry is scheduled for it. The verified retention evaluation time stays fixed through loading the selected manifests and deletion planning. Foreground preemption preserves its actual cancellation reason and waits for all active readers to settle; a later history observation may legitimately renew the pending request. Deletion still uses its existing short allowance and bounded entry count. Large finite backlogs and object GC continue through governed passes until verified completion. A busy device still finishes: a version landing during cleanup makes the next pass plan again, and that pass reads only what is new (tested with 200 versions, 3 s per read and a new version every two minutes).

## Sync through Drive

Every device stays fully local. Whenever Drive is signed in, the device syncs with it: Drive is where a person's devices meet. The Device Folder is this device's own copy and never a second sync channel. The app works the same with either location, both or neither.

- **Shared base.** Each device keeps what it last shared through Drive (`reconciliationBase`, header v5; an older base is dropped by the compatibility layer at start-up and the next sync records a fresh one): note titles and text, fingerprints per Saved Day (rows `reconciliationBaseDays:YYYY-MM`) and of the Active Session, both of the whole record and of its study content only (save times and owner left out), and one fingerprint for each setting, the Plan draft, the default plan and each saved plan, with the verified Drive checkpoint id. If this device cannot save its new base after a sync or upload, the work stays done but the status does not say Synced, and sync retries. Only a verified shared Drive head moves it: a successful Drive publication or taking in/Combining Drive's newest verified shared head. Drive's newest is taken from a fresh listing for this. Device Folder versions, Replace and add-what's-missing never impersonate Drive ancestry and never move the shared base.
- **Catch up first.** On sign-in, start, a return to the app (at most once a minute), going to the background and every 20 minutes, the device compares Drive's newest version with its base. When Drive moved on, it takes that version in by a quiet Combine (`sync: true`) before uploading anything. What changed on one side only since the base is taken from that side. A note whose text changed on both sides in different paragraphs is joined by Smart merge (`mergeThreeWay`, only when it reports `safe`). Anything else changed on both sides never stops the sync: the newer shows and the other is kept for review (below). Timestamps never settle a difference; they only choose what shows until the person reviews it. Only a version the sync cannot settle that way (an older backup format, or more kept versions than may wait) stops it without changing anything; the Drive row and the status indicator then show "Needs review", and Review opens Combine on that version.
- **Plans and settings merge per item.** Each setting, the Plan draft, the default plan and each saved plan (by id; label and schedule, not timestamps) is compared with the shared base on its own. The Plan draft is one value shared by all of a person's devices (owner's decision, 2026-11-07): clearing or changing it on one device changes it on the others, and if both changed it, the other version is kept for review. A change on one side is taken; only the same item changed on both sides is kept for review, and the review shows just that item (a full Plan draft or saved plan comparison opens in the dialog). Saved plans added on both sides are all kept; their order counts only for plans both sides hold. A device whose plans and settings are all unset never causes a review.
- **Session ownership record.** The Drive record of which device runs today's session is format v4 (see [study-session.md](study-session.md#moving-a-session)); this build writes only v4. Claims an older device writes (v2, v3 or the plain form) are read through the compatibility block in `backup-provider.js`. Builds before it cannot read v4, so update every device at about the same time.
- **Kept for review.** A version a sync did not show is kept as a `PendingReview` record (appMeta `pendingReview:<id>`, one row each; contract `PendingReview.v2`): a note's other text or title with what both last shared, a note deleted on the other side (`kept: null`; the note stays), a Saved Day or its deletion, plans and settings, or a session. It records where it came from: `keptFrom`, the installation ID of the device whose copy held it (this device for its own copy; for the version taken in, the device that made that version; for a session, the device it ran on), and `keptChangedAt`, when that copy last changed it (the item's own time, or that version's last change for plans and settings). The review names the device as backup folders do ("From iPad · Safari, changed 06 Nov, 21:40"; "this device"); a v1 record, kept before this, says the device was not recorded. It is synced data: it goes into every version (backup v24 entity `pendingReview`, manifest 9 unit `pendingReview:<id>`), reaches every device, never expires, and ends only when the person resolves it on any device (the record then keeps only its id, and a resolved one wins every merge). Two open reviews of the same item with the same content, made on different devices, merge into one. At most `maxPendingReviews` (2000) may wait; more stops the write and nothing is dropped. Images a kept version uses are kept like any other reference. A note with one shows a quiet "Needs review" mark; Library → Data and the status indicator show the count. Review (`reviewKeptVersions`) asks the choices first (titles, deletions, Saved Days, plans and settings, the session), then note texts in the comparison dialog (current against kept, with Smart merge from what both last shared). Nothing is written until both are confirmed, nothing that changed meanwhile is overwritten (that review simply waits), and each choice is an ordinary edit that syncs. A kept session waits while a session runs here; a used one is set aside as suspended, ready to continue. Reviewing never opens by itself. Copy diagnostics lists each open one (`Kept version`, newest 12): subject, cause (`note-text`, `note-title`, `note-deletion`, `saved-day`, `settings`, `session`…), device (type and browser, "this device" or "not recorded") and times, never its content or which note or day.
- **Upload.** A Drive upload is refused when Drive's newest version is not the base (another device uploaded meanwhile): the device catches up and the upload follows. Drive's newer changes come in first and never wait for another device: only this device's own upload waits its turn, so a device always has the latest while it waits. When another device's upload started first and is still running, this device's upload waits its turn, retrying after 15 s, 30 s, 1 minute and then every 2 minutes; its own markers never block it. Sync now, shown only while waiting, uploads once without waiting for the turn. A marker from this build renews every 2 minutes and holds the turn only while it keeps renewing (5 minutes without a renewal means the page closed or froze mid-upload); a marker from an older build, which never renews, holds it for 15 minutes from its start. Turns only save wasted work: every upload checks again just before its commit that Drive has not moved on (another device's Sync now, or this device frozen past its turn). If it has, it commits nothing, catches up and uploads again, reusing the pieces it already uploaded, so a large attachment is not sent twice: cleanup removes no piece while any upload marker is there and keeps unreferenced pieces 48 hours, and the retry uses only those still listed. Two commits landing in the same instant, after both checks, can still both land on the same base; the next sync then treats every difference as made on both sides (the newer shows, the other is kept for review), so nothing is lost. While waiting, the status says which device holds the turn ("Waiting for Windows · Chrome to finish saving…"), and Copy diagnostics shows it with when that upload began and last renewed (`waitingFor`, `waitingSince`, `waitingRenewedAt`; type and browser only).
- **Upload markers renew.** An upload's marker is renewed every 2 minutes while it runs (on Drive by a fresh marker that keeps the upload's start time; in the Device Folder by rewriting the lock), and, before its commit, once more if its last renewal is 2 minutes old or more; the commit then checks the marker is still there. Cleanup treats a renewing marker left unrenewed for 15 minutes as abandoned (a closed or frozen page), removes it and runs; the upload, if it ever resumes, fails its renewal and commits nothing. A marker from an older build that does not renew still holds cleanup back for its full day. Cleanup that waited for uploads is retried when the blocking marker could lapse, and early only when this device's own upload ends with no other live upload left (`repository-policy.js`: `publicationRenewMs`, `publicationStaleMs`).
- **Password.** The newest version says which password it uses (`protectionId`). When another device set or changed it, a quiet catch-up stops with "Needs password" (status indicator and Drive row); entering it there continues the sync, and the password typed for that version is kept on this device under the library's id (`BackupProtection.follow`). A plain version built on an encrypted one means the password was removed elsewhere; it is removed here too.
- **Status.** Shown by the profile indicator ([status-indicator.md](status-indicator.md)).
- **Plans and settings with nothing more.** When both sides changed plans and settings (or never shared them), a side that holds nothing the other lacks takes the other's and nothing is kept: every setting unset or equal, the draft empty, the starter plan or equal, every saved plan present and identical, and the default plan unset or equal. A fresh device's start-up state therefore takes the library's on its first sync. When both hold something the other lacks and they never shared plans and settings (a device whose database was removed, say), nothing missing counts as deleted: every saved plan either side holds is kept, this device's value stays where both set the same thing differently, the other's is taken where only it sets one, and only such a clash is kept for review. Otherwise a device with no shared history would publish a copy without the other devices' saved plans, and they would lose them. With a shared base that lacks per-item detail, this device's copy stays whole and the other is kept for review, since an empty field there may be a deletion.
- **Known limits.** A fresh device that skips the first-start form and connects Drive later, with plans or settings it changed itself, keeps the other side's for review on its first sync (joining from the first-start form takes the library's). A kept session the person uses comes back as suspended on this device; the device running the session carries on until it syncs that change.
- **Active Session.** Which device runs today's session, and how it moves between devices, is in [study-session.md](study-session.md).

## Sync decisions

The owner settled these over several rounds (2026-10-17 to 10-25); do not reopen them without the owner. The app is meant mainly for one device; two or three per person is the most it must handle well.

| Part | Decision |
|---|---|
| When | Whenever a Drive sign-in is open. Google gives about an hour, renewed only by a tap; sync simply happens in those windows. No refresh token and no server |
| Upload cadence | 20 minutes after the first change; the owner chose not to shorten it |
| Order | Catch up first, then upload. A device never uploads over a Drive version it has not merged; if Drive moved on meanwhile, the upload is refused and the device catches up again, without asking |
| Two devices open together | No device lock (a Web Lock works only inside one browser; a Drive lock would stop the other device). Catching up on return shows the other device's edits before you type |
| Three devices | Each merges only with Drive, which already holds the others' changes, so a choice is always between two versions |
| Running session | Restore and Combine are blocked while a session runs; sync is not. Everything else merges; changes to the running session itself wait |
| Combine and Replace | Not part of everyday Drive use. They stay for backup files and Device Folder versions. Restoring a Drive version applies to every device, with a safety version kept first |
| Device Folder | This device's own copy, never a second sync channel |
| First sync with no shared history | Two-way merge: anything on one side only is added, anything different on both is kept for review |
| Data from a newer version | Held untouched and shown read-only; nothing converted, merged or deleted ([data-and-storage.md](data-and-storage.md#data-this-version-cannot-read)) |

**Merge rules (2026-10-18).** The person's data is never lost. Merging is automatic wherever it is lossless; only genuine conflicts are shown, never as a pop-up during study, and timestamps only choose what shows until the person reviews.

| Case | Result |
|---|---|
| Changed on one side only since the last sync | That change is taken |
| Note changed on both, in different paragraphs | Smart merge (`mergeThreeWay`, only when it reports `safe`) |
| Note changed on both in the same paragraph, or renamed on both | The newer shows; the other is kept for review |
| Note edited on one device, deleted on the other | The note stays; the review offers to delete it |
| Saved Day, plans and settings, or the session changed on both | The newer shows; the other is kept for review |
| Attachments | Added on either side are kept (content-addressed); deletions follow deletion records |

**Edge cases.**

| Case | Behaviour |
|---|---|
| Browser data cleared | An unresolved clear never uploads; the device downloads again |
| Offline for months | Merges normally; deletions older than the kept deletion records may reappear |
| Clocks differ | Clocks only choose what shows before review. A version is always stamped after the version it is built on, whatever the device's clock says, so a clock running behind or ahead never keeps a device's uploads from becoming Drive's newest. Upload and cleanup markers are aged on Drive's clock, which the Drive adapter learns from the markers it creates (`repository.now`), so a wrong clock neither removes another device's live marker nor waits for one long gone |
| A note open in the editor when a change arrives | Updates in place if nothing was typed since the last save; otherwise a both-changed case |
| Password added or changed elsewhere | Other devices ask for it at their next sync |
| Drive full or unreachable | Sync pauses; the app carries on locally |
| Large attachments on mobile | Downloaded only when missing |

**Known limits.** A fresh device that skips the first-start form and connects Drive later, with plans or settings it changed itself, keeps the other side's for review on its first sync. A kept session the person uses comes back suspended. A device that never signs in to Drive again keeps a profile deleted elsewhere; Device Folder backups of a deleted profile on other devices go when those devices remove it; deleting everywhere needs Drive signed in. Drive flows are tested against a simulated Drive, not real Google. Two people on one Google account are refused by design.

## Profiles on Drive and in the Device Folder

Each profile has its own library: its own database, Device Folder repository and Drive library ([data-and-storage.md](data-and-storage.md#profiles-and-devices)). A profile id is `prof_<name>_<time>_<random>`.

- **Drive library.** The Drive folder carries its profile's id (appProperty `studyDirectorProfile`). Once per sign-in, before any Drive operation, Drive tells the app the account email and what the folder holds (`api.backup.profile.bind`), and the app settles it: its own folder continues; an unmarked folder (from before profiles) is claimed; a library from another device is offered as "Continue with your library?" with its counts and date (only within 5 minutes of tapping Connect), and the profile takes its id; a library or email that belongs to another profile on this device is refused without touching anything, and the sign-in is forgotten. A newly bound folder clears the shared base, so the first sync is a two-way merge.
- **Password.** The record (`BackupProtection.v3`) keeps a non-extractable key next to the verifier. With one profile on the device it opens the profile at start; with two or more, each start asks ("Not now" keeps sync and encrypted backups waiting). Sync follows the library's password (above).
- **First start.** Someone new gives a name, an optional password and optionally connects Drive; the password is set before Drive is used, so no unencrypted version reaches it.
- **Backup folders.** Names are for people; markers say whose a folder is. Drive: "Study Director – Ana", renamed once per sign-in to follow the profile name (found by its properties, never by name). Device Folder: one folder per profile and device inside the chosen folder, "Study Director - Ana - iPhone Safari" (" (2)" when the name is taken; plain ASCII only, accents dropped and other scripts left out, because some file systems map other characters onto another folder: Chromium's own browser storage hands back the chosen folder itself; a new folder must also show up in the folder's listing under its name), known by `repository.sdscope` version 2 (`{id, profile, scope, device}`); its id is kept when it is moved or taken over, so what was verified stays verified. The controller settles the folder before any backup (`prepareRepository`): its own; else the single folder of earlier versions (`Study-Director-Automatic-Backup-Repository`, `~<scope>` for later profiles) copied in and checked, then deleted (the marker records `moving`, then `movedFrom`; an interrupted move continues); else, when a folder is chosen, one of another device's folders (after a browser data clear) or a new one; else a new one.
- **Deleting a profile everywhere.** The deleting device leaves a marker in Drive first (a folder "Study Director – Ana (deleted)" with appProperty `studyDirectorDeletedProfile=<profile id>`, without the library marker), then moves the library folder to the Drive Trash and deletes its own Device Folder backup folder for the profile. Every device checks for the marker once per sign-in, before it finds or makes the library (`resolveFolder`), and tells the app (`api.backup.profile.deleted`): a device with nothing Drive did not have removes the profile; otherwise the person chooses. A device that keeps it gives it a new id (`Profiles.renew`), so it never meets the marker again.

## One format

Every new version is written in the current format (manifest 9; backup files v24). Older versions are only read. A build that cannot read a newer version keeps it, uploads nothing over it and asks for an update (F18 says so, "has a version this app can’t read"), so update every device at about the same time.

- **Old versions retire.** Once a location holds a current version, older ones leave Version History and the next cleanup removes them (`selectRepositoryRetention`), except one newer than every current version: a device still on the older build made it, and it may hold work not yet taken in, so it stays until a newer current version replaces it. The Device Folder's old single folder is moved into the named one. Copy diagnostics, "Format cleanup": `canonical` and `retirementReady` (this device's data, `verifyCanonicalInstallation`), `oldFolder` (the Device Folder's old folder still there), and per connected location `currentVersions`, `olderVersions` and `unreadableVersions` as its last cleanup left them; the row reads ready when all agree. Version History follows the same rule from the listing's format, before any cleanup runs.
- **Release B (not yet).** A later, separate release removes the code that reads older formats (compatibility entries `backup-repository-v1-v4` and `device-folder-single-repository`). It ships only after "Format cleanup" reads ready on every device in use.

## Standalone backup files

A backup file stays one self-contained file covering everything, not a repository: gzip-compressed metadata followed by the attachments as they are (they are already compressed), optionally sealed in authenticated AES-GCM frames. It shares the capture, the codec and the file worker with the engine, and nothing else.

- **Export.** The save dialog opens from the click itself, so the browser allows it and the status line answers at once. After a location is chosen the backup is captured, packaged into a private scratch file, verified by a full self-restore check, optionally encrypted, written to the chosen file and read back; the saved file must match byte for byte. Each step and its byte progress show as it happens. Browsers without a save dialog download the verified file instead. A file saved and read back counts for the backup reminder; a started download does not.
- **File worker.** One SHA-256 for every file checksum in the app (files up to 32 MB use the browser's own; larger ones stream through a fast incremental one), byte comparison a word at a time, and AES-GCM with four 1 MB frames in flight. Reads stay bounded to one frame.
- **Measured** on 200 MB of attachments: export 2.5 s (5.3 s encrypted), save and verify through the dialog 4.6 s, check before restore 1.1 s. Before this work: 10.2 s, 17.1 s and 4.9 s.

## Foreground and background work

Foreground backup/restore publication has priority over background repository maintenance.

Maintenance is bounded by the shared repository work budget. Provider-visible maintenance markers behave as bounded leases: a marker remains authoritative only through the allowed work budget plus bounded release/network grace. An abandoned marker can therefore be reaped by a later foreground operation instead of blocking Backup/Restore for an extended period.

Background maintenance intent is durable only when useful, and it is scoped to the repository generation that created it.

Background admission rechecks the complete active set after awaiting a retiring executor. If another contender acquired during the wait, higher-priority work aborts that lower executor and declines admission until the existing retry path can observe its actual release. It never overlaps an executor whose settlement was not awaited.

## Repository identity and external deletion

A Drive repository is identified by its actual Drive folder generation. If a cached folder has been deleted or moved to Trash, the Drive transport invalidates the stale identity, rediscovers or creates the repository, and continues the same foreground operation.

When the repository generation changes, provider-session state tied to the previous repository is discarded, including cached/verified history, convergence retry state and stale maintenance intent. The same scoping also applies across application restarts through durable maintenance metadata.

For Device Folder, deleting Study Director's repository subfolder is self-healing because required repository directories are recreated. Browser permission state is treated separately from folder identity: a temporary permission lapse keeps the configured directory handle and offers permission renewal on that same folder. Only a genuinely missing/unusable parent handle returns the app to folder selection.

## Google Drive connection

The Library → Data row distinguishes configuration/history from live authorization.

- Never connected: offers Connect/Recover.
- Live authorization: offers Back up now / Versions / Settings.
- Expired or invalid authorization: shows Reconnect required.

Known token expiry, a Drive `401`, explicit disconnect and visibility re-entry update the UI state. External revocation cannot be known without a Google request; the next Drive request detects it and immediately transitions the UI to reconnect-required state.

Drive JSON metadata is consumed once inside the original 45-second request timeout and abort lifetime. Binary uploads use asynchronous browser upload-progress events; a 120-second inactivity watchdog renews only when the byte count increases. Both multipart files and resumable chunks can therefore take many minutes while progressing. Range downloads use the same 120-second byte-inactivity rule, retain the one-MiB range limit and revalidate immutable size/digest/version. Empty chunks and repeated byte counts do not prolong stalled work. Request cancellation aborts the transport and releases listeners and timers; upload acceptance still requires the server SHA-256 receipt. The fetch-only capability fallback retains a finite request deadline because it cannot observe upload bytes. Retry/error handlers and metadata callers share that parsed payload. Interrupted, malformed or invalid-shape responses fail; they are not empty inventory. Successful media responses retain the existing bounded streaming owner, while header-only 204/308/401 outcomes do not wait for unused bodies. Copied developer updater states preserve checking and downloading.

- **Resumable uploads.** Small repository files use verified multipart upload; larger ones use 2 MiB resumable chunks, a validated Google upload-session URL, and server-acknowledged offsets. In the *same open page*, interrupted uploads can poll Google's acknowledged position and continue; expired sessions start anew, and an ambiguous completion is reconciled against the exact marked remote file. XHR byte-progress is never treated as a durable server receipt. A page/process termination loses the **in-memory** resumable URL and offset: on the next opening, the repository reconstructs from canonical local data and may resend an uncommitted large object. Persisting short-lived upload URLs and offsets across page restarts was deliberately rejected without measured benefit sufficient to justify new sensitive state and recovery complexity; this does not claim uninterrupted/background transfer while the PWA is closed. Every upload, including an optimistic supposedly-new identity, first queries its exact marked Drive identity **by metadata only**, rejecting duplicates, unsafe existing metadata, incompatible content and a conflicting reported server SHA-256. This costs one small metadata lookup per freshly uploaded file but avoids replay collisions without downloading the file's bytes or signing in again while existing authorization remains valid. New object, manifest and commit receipts are checked independently; no checkpoint becomes committed merely because a chunk was sent or a session existed. Retry/orphan cleanup remain under the shared repository engine and are separate from Device Folder.

## Device Folder permission

Device Folder passive permission observations are ordered by a controller-local generation and bound to the exact directory handle they queried. A superseded async answer cannot overwrite a newer grant, revocation, reconnect, folder replacement or disconnect. Start-up folder rehydration follows the same generation fence, while the folder picker and `requestPermission()` are still invoked directly from the user's click. Passive refresh never requests permission, and it does not compete with an active authorization. The existing transport, repository locks, verified backup and connection notifications remain unchanged.

Library → Data → Copy diagnostics includes the current permission and a capped, nonnegative `stalePermissionResponses` count (per open controller, not persisted). It helps explain discarded out-of-order observations without recording directory handles, folder names, note text, file paths, credentials or tokens. Existing bounded operation phase timing and inventory milestones remain the primary performance diagnostics; no new CPU sampler, background daemon or trace log is installed.

## Integrity

Repository integrity metadata lives in the device-local `repositoryIntegrityScrub` record, version 7, keyed by location id (`device-folder`, `google-drive`; at most eight). Each location carries its repository identity, scan identity, verified cursor, completion/failure dates and quarantined object IDs. Both locations use the transport's repository scope: Drive's verification scope, and the random identity file inside the Device Folder repository, so folder replacement or recreation starts a new cycle. The ordinary runtime reads only version 7. The compatibility host converts the released version-2 to version-5 records once at start-up (they kept fixed `device`/`drive` slots; version 6 came only from unreleased builds and is refused), dropping the directory handle older records kept and failing closed on unknown shapes; unscoped version-2 completion/quarantine derivations are invalidated when a target is first bound to a proven repository identity.

Target changes and progress updates use a strict appMeta readwrite transaction. Failed reads cannot become default state that overwrites another provider, and failed writes/commits reject the checkpoint. The write chain remains usable after rejection. Ownership and repository identity are checked before accepting results; a stale scan cannot populate the replacement repository's state. Quarantine consumers use the same identity-bound reads. Valid quarantine and exclusion IDs are deduplicated without truncation in host state, shared repository policy and provider adapters. History filtering, selected-version restore, repair publication and scrub traversal honor the entire set. Object/byte/segment pass limits still bound verification work; a failed metadata commit preserves the previous record rather than consuming progress.

The managed repository scrub hashes the ordered object inventory into a scan identity. Where the location reports a stored digest for each object (Drive's server SHA-256, read from the object listing), the scrub compares it with the recorded checksum instead of downloading the object; a mismatch is corruption. Such objects use no byte budget. The Device Folder reports no digest, so its objects are read and hashed. A cursor is resumable only against that identity; inventory changes restart the cycle so objects inserted before an old cursor cannot be silently skipped. After each complete object verification, an awaited progress callback commits its cursor before the executor yields. Errors and aborts carry the last verified progress. Object/byte batch limits remain bounded, with the first oversized object permitted. The shared integrity policy uses a 120-second cooperative allowance, independently of shorter retention-maintenance budgets. The scheduler checks elapsed time only after an awaited durable checkpoint advances verified bytes, frames or an object cursor; scratch initialization alone cannot consume the opportunity. A slow, progressing segment may finish beyond the allowance before yielding. Foreground cancellation remains active throughout preparation, transport and hashing. The private integrity continuation capability persists one-MiB stored-byte hash/offset checkpoints after scratch writes flush, with at most 32 segments per opportunity. Device snapshots bind size/mtime; Drive validates exact bounded ranges and version before/after a read. Changed versions or missing staging reset only that object. Resumed plaintext passes revalidate the current source version, including after a long key lock. Authentication failure compares bounded source ranges with the failing staged frame so damaged local ciphertext can restart without declaring repository corruption or repeating an unbounded hash. Streaming encrypted objects resume plaintext hash and authenticated frames, including the terminal frame. Historical encrypted objects retain the existing bounded compatibility reader. Structured objects retain their semantic checks, with scratch verification separating local staging damage from repository corruption. Staging files use shared producer/read leases, strict metadata retention and scoped file-worker lifetime. Password/key material never enters metadata.

Explicit stored/plaintext digest or size mismatches, verified JSON/identity/member failures, and authoritative missing-object results may quarantine an object and request the existing repair publication. Transport timeout, permission, key-lock, cancellation, unknown reader results and unreadable/incomplete history are unavailable or yielded outcomes. They do not manufacture corruption or trigger repair writes. A completed cycle that still contains quarantined objects retains its warning; partial progress preserves unresolved failure state. Explicit Device Folder and Drive rechecks include quarantined objects, removing each only after full successful verification. Recheck request identities keep results from older scans from settling a recheck: their progress and findings are refused, but a clean full pass that was already running when Recheck was pressed is still recorded as the last full scan (it used to vanish, so Recheck seemed to do nothing), and the recheck stays pending. Library → Data → Verification shows, per location, a plain headline (checking with live progress, checking in small batches, paused and why, recheck requested, all backup files intact, or damaged files) and when the last full check finished; Recheck answers at once and reports a failure in its own row. A run that stops at its batch limit reports `budget`; a failed read is reported by its kind (permission, busy, unavailable), never by its message. Rechecks remain pending through unavailable or locked outcomes. A separate inventory-bound attempted cursor durably records each fully checked recheck failure; the verified cursor advances only for healthy objects. Still-corrupt quarantined objects consume batch budgets and remain quarantined while later candidates are verified. Earlier corruption does not discard a later object's segment checkpoint. A full recheck with remaining corruption ends the request with a failed outcome and warning, without repeatedly publishing repairs for already known failures. Newly discovered corruption retains the existing repair path; a new request or changed repository/inventory invalidates old attempt progress.

Yielded work continues after two minutes; metadata failures retain a five-minute retry, unavailable verification uses ten minutes, and locked protection uses thirty minutes. Existing corruption retry and fourteen-day recurrence remain separate. A recent previous completion cannot suppress an unfinished cycle or failure. Startup metadata failures also retain retry opportunities. Device Folder permission restoration and write-control takeover provide a fresh scheduling opportunity without requesting permission; ordinary focus on a connected target leaves the existing cadence intact. State is published as healthy only after the relevant durable checkpoint succeeds.

## Publication failure and retry

Publication error handling cannot use a successfully returned upload receipt as evidence that the attempt **created** an immutable file. Device Folder may reuse an identical file and Google Drive may recover an upload whose response was lost. A manifest, commit or object may even have become visible before verification failed. Therefore the publication failure path **does not delete** manifest, commit or object identities. Pending/uncommitted artifacts are candidates for later inventory-verified, reference-aware retention/garbage collection under the existing repository maintenance contract; an orphan manifest alone never counts as a committed recovery point. This also protects previously committed checkpoints from mistaken retry cleanup.

Device Folder deletion now checks an explicitly supplied SHA-256 digest against the current bytes as well as a supplied remoteVersion. The same no-guessing deletion rule already applies to Google Drive metadata. Uncertain versions refuse deletion rather than relaxing repository safety.

Convergence's failed attempt captures the canonical revision it began with. Same-revision failure or turn backoff replaces its own deadline; a genuinely different current revision retains any earlier urgent deadline. Pending-retry diagnostics retain the actual cause rather than labelling all failures as managed recovery. Managed recovery records independent durable pending intents for the source and every configured automatic peer (including temporarily disconnected destinations); each is cleared after its own verified publication. Unconfigured or explicitly forgotten destinations do not retain an obligation. Coverage rediscovery remains a second line of defence after restart.

Automatic Drive catch-up uses suspension-aware admission. Its own managed-recovery suspension retains precisely that initiating sync controller, so it can finish local reconciliation; a separate PWA update, file-backup or storage-reset suspension still aborts it and waits for real settlement. Automatic sync also declares its shared import controller as background-preemptible, preventing the standalone file-work observer from acquiring a self-cancelling `file-backup` hold; manual file imports and exports still suspend provider background work. The portable-file Cancel control is not shown during a quiet provider catch-up. The startup canonical mutation-clock reconciliation now fails closed on an unavailable authoritative read, and a failed promise is not cached as a successful prerequisite. No new scheduler, storage family or backup topology was introduced.

- **Source revision.** IndexedDB's canonical mutation epoch remains authoritative. The fast backup revision now selects the newest valid timestamp from the in-memory storage-health projection and its localStorage mirror, so a failed mirror write cannot hide a newer committed mutation in the same tab. Startup runs one shared change-clock reconciliation promise and awaits it before opening background-owner activation; Device Folder installation uses the same prerequisite.

## Presentation

`backup-presentation` is a stateless adapter over `notice-coordinator`: Device Folder, Google Drive, portable files and managed recovery use the same scoped event handles. The coordinator retains messages, typed progress, severity, lifecycle, dismissal and delivery deadlines. Controllers retain execution leases, signals, repository state and verified checkpoint metadata. Existing dialogs, backup rows and toasts project coordinator state without separate message caches.

Recovery lends its scoped handle to nested provider work; only the outer operation publishes the final result. Local recovery completion, pending external convergence and verified external backup are distinct outcomes. Background convergence uses a separate event identity so it cannot overwrite local recovery progress. Foreground completion has one expiring confirmation while its inline result remains available; automatic success only refreshes status. Permission and repeated-failure conditions have stable identities, contextual actions and explicit resolution. Normal maintenance deferral remains diagnostic.

The engine and the backup runtime draw nothing. The app draws the portable-file row (Export, Cancel and its note) from the backup controller's status and the `file` presentation, and the Device Folder and Drive rows from `locationStatus` and presentation events, with the same parts: Connect (Choose folder… for the Device Folder), Back up now, Cancel while an operation can be cancelled, Versions, and Settings that open in place with Disconnect. Each row has one inline note showing `BackupPresentation.current(source)`: the running operation, otherwise the newest of its last operation, automatic backup or status message. Drive connects in one click; sign-in is prepared while background work gives way. With backup encryption on and locked, a connected row reads "Needs password" rather than claiming automatic backups are on; so does Drive when a sync finds a password set or changed on another device. Library → Data states once how far back versions go (15: the latest, 6 daily, 4 weekly, 4 monthly). Getting data back uses one verb family: Versions, then Restore… (Add only what's missing, Combine with current data, Replace current data), Restore note… or Restore from file…. Device Folder and Drive rows use the same stateless location/result formatters. Resting state is `On · Last verified HH:mm` for today's verification (with a date for older verification); running state describes backup, restore, combine or history work. Typed progress appears in the existing inline operation summary. Successful summaries gain one visual tick without changing the underlying event or replaying delivery. A local recovery tick does not promote pending external backup to verified. Durable verification metadata remains intact; the redundant global freshness row and its save/drawer callbacks are removed.
