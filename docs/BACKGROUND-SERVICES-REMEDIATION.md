### 0.3 CLEER / architecture invariants

- **Clean, Lean, Efficient, Elegant, Robust, Reliable.** Single owner per responsibility; bounded work and observable settlement; no busy-loop polling or duplicate scheduler.
- Canonical local data, Note rescue and Active Session progress have greater authority than a transient timer, notification, cache or provider timestamp.
- A lost/timed-out job never implies underlying native I/O stopped; actual settlement, leases and durable cursors remain mandatory.
- Foreground mutation, restore, clearing and update application take priority; unknown references, unreadable schemas and disconnected providers never authorize destructive cleanup.
- Strict attachment reachability and journal/restore scratch pins; Device Folder and Drive independent destinations; Drive shared catch-up never overwrites a newer verified head.
- Preserve install-time SW hash verification and existing low-latency user experience; hash every ordinary file read only if a new explicit reliability contract justifies it.
- PWA background work is opportunistic while executable, not a guaranteed OS service when closed. No new server/native scheduler presumed.
- No owner data, Note text, URLs, account details, tokens, raw backup objects or unbounded diagnostic traces in repo, logs or QA.
- No push to `main`, merge, deployment, release, workflow/settings edit, format migration or broad refactor without separate authorization.

- Claiming there is no shared lifecycle or no foreground preemption — current source has both.

  - **The thrown message.** Temporary logging, since removed, captured it: `Pending-review reconciliation commit did not match the resolved state for pr_…`. The id was the review A held open and Drive held resolved. For that id, the stored row was the correct resolved review, but the stage's own expected value was `null`.
  - **Cause 1 — missing limit.** `app.html` hands the Backup module a hand-picked `limits` object. That object has no `maxPendingReviews` (and no `maxNoteLinks`). In `backup.js`, `PendingReviewCodec.merge(lists, undefined)` keeps `Math.max(0, Number(undefined)||0)`, which is 0 resolved reviews. The repository's own merge uses the real limit (2000), so it writes the resolved review while the restore stage expects it gone. The commit check then throws on every sync that brings in or changes a resolved review. Integration tests pass the full limits object, so they never saw the gap. No browser test resolves a kept version on one device and syncs it to another.
  - **Other effects of the same missing limit:**
    - `replacePortableCanonicalSnapshot` is used by rollback and by whole-version Replace. With the zero limit it writes the target reviews without any resolved ones, so each failed attempt deleted this device's resolved-review records. Verification compared against the same reduced list and passed.
    - `replacementSnapshot` drops resolved reviews from the journal merge in the same way.
    - The "more than N versions would wait" guard compares against `undefined`, so it never fires in `backup.js`. The repository still enforces it.
    - `maxNoteLinks` is missing too, so `slice(0, undefined)` does not cap the union of two notes' links when combining.
    - No note, Saved Day, session or settings data was affected. Resolved-review records live on Drive in every checkpoint, so the next successful sync brings them back ("a resolved one wins").

With the rollback reporting a data change (as it does in the app: the diagnostics show `provider-convergence` starting with `reason=important-change` 0.3 s after each failure), there were **120 attempts in 10 minutes**, one per fixture step. Without that report, attempts came at 0, 10, 45 and 170 s. Why: the rollback's own writes move the canonical revision and call `noteChange`. The backoff therefore treats them as a newer local edit that deserves its own urgent catch-up, which is correct for a network failure but not for a deterministic one. The same Drive version is then downloaded, applied and rolled back again every few seconds.
- **Step 2 — objectives before edits:**
  - **E22.1** The Backup module receives `maxPendingReviews` and `maxNoteLinks`, the two limits `backup.js` reads without a fallback.

### Entry 023 — Drive backups slower than before, and a "Needs review" that keeps showing (2026-11-01)

- **Branch / source HEAD before:** `refactor/background-coordination` at `61e4e1a` (same tree as `main`, release `SDVB75F16`). The owner reported that Drive backups are much slower than before and that the app keeps asking for review. Their Copy diagnostics show `provider-backup` taking about 20 s for 1.3 KB, `keptVersions=1`, `needsReview=false`, and Drive maintenance deferred with `publication-contention`.
- **Step 1 — audit and reproduction:**
  - **Speed.** A probe on the release build gave every simulated Drive request 300 ms of latency and timed three small backups. It then compared the result with the same probe on `9afbda7` (the build before the Drive identity and session-claim passes). Results: now 18 requests in about 4.1 s; before, 14 requests in about 2.9 s. Recording the start time of each request showed 13 serial steps per backup:
    1. folder check;
    2. lease POST;
    3. discovery (folder, maintenance, object, checkpoint and commit lists, all at once);
    4. publication list (`assertSharedPublicationTurn`);
    5. session-claim read (`assertSharedSessionOwnership`);
    6. object identity lookup;
    7. object upload;
    8. manifest identity lookup;
    9. manifest upload;
    10. lease check and maintenance list;
    11. commit identity lookup;
    12. commit upload;
    13. lease DELETE.
  - **Where the extra steps came from.** Three of the four new steps are the pre-upload identity lookups `drive.js` now makes before every upload (`c0642a1`, `7ab67f0`; a presumed-new identity is not proof of absence after a restart). The fourth is the Active Session claim read (`d089a6b`). The read-back verifications are not extra requests on Drive: the upload response carries Drive's SHA-256, so the provider's verifiers return without downloading. At real Drive latency (about 1–1.5 s per step on a phone), 13 serial steps account for the owner's 20 s.
  - **What must stay serial.** The identity lookups and the lease check before the commit are deliberate safety steps and stay. The commit must follow every object and the manifest. Otherwise:
    - steps 4 and 5 only read (publication markers and the session claim), and need only the lease, which already exists at step 3;
    - the manifest does not depend on the object uploads. It is finalized from the prepared checkpoint, which is immutable once prepared, and it stays invisible to every reader until its commit exists. An uncommitted manifest left by a failed attempt is already found and removed by maintenance (`inventory.uncommitted`), and a retained continuation reuses the same manifest file, so the lookup finds and adopts it on retry.
  - **Review.** A two-browser probe: the laptop (A) runs today's session and edits a note each round, and the phone (B) only connects and syncs. B's first sync keeps a `personal` review. That review travels to A, and both devices then show "Needs review" (count 1) indefinitely. The kept value is B's start-up state: every preference `null`, no saved plans, and a draft equal to the plan B had just taken in. It holds nothing the shown version lacks. Cause: `personalSettled` returns null when there is no shared base fingerprint (a device's first sync), so the sync keeps the hidden side whenever the two differ, even when the hidden side is a subset of the shown one. After that review was resolved, four further rounds kept nothing new.
