This statement describes Study Director's security model and responsible vulnerability-reporting process. It is intended to explain safeguards and reporting expectations; it is not a representation that any software or service can be completely free of defects or security risk.

1. Security model

  • Local-first storage: core study records remain in browser/device storage by default instead of being copied to a Study Director application database.
  • Transport security: the public web application is served over HTTPS by Firebase Hosting.
  • Browser controls: the production Hosting configuration uses a restrictive Content Security Policy and additional response headers intended to reduce script-injection, framing and unnecessary browser-permission risks.
  • Google Drive least privilege: optional Drive access requests only the drive.file scope.
  • Short-lived authorization: the Study Director Drive provider keeps its OAuth access token in memory and in this browser's localStorage only until it expires (about an hour), so a reload does not ask for a new sign-in. It is removed on expiry, disconnection or rejection. No refresh token is requested or stored.
  • Backup integrity: Study Director verifies supported backups, including per-image SHA-256 checks in binary-framed backup v10 and SHA-256 read-back checks for Drive operations. Integrity verification is not encryption. Optional encrypted backups use native AES-256-GCM with authenticated headers and PBKDF2-HMAC-SHA-256 (600,000 iterations). Encryption covers backup contents; it does not encrypt browser storage or internal recovery journals.
  • Defensive restore: backup imports are validated and previewed before destructive restore operations are committed.

2. User responsibilities

Protect your device account, browser profile, downloaded backup files and Google account. Use device encryption, current software and strong account authentication where available. Keep an independent backup of important study information and do not share OAuth tokens, passwords or private backup files with untrusted parties.

3. Reporting a vulnerability

Report suspected security vulnerabilities privately to shubhamtiwari1212@gmail.com. A useful report should include the affected Study Director version, browser/device context where relevant, reproducible steps, expected and observed behaviour, the likely security impact, and the minimum evidence necessary to demonstrate the issue. Please do not send passwords, OAuth tokens, another person's personal data, or unnecessary backup contents.

We will make reasonable efforts to acknowledge and triage genuine security reports and to investigate material vulnerabilities. This statement does not create a bug-bounty programme or promise payment.

4. Responsible security testing

Good-faith testing must be confined to systems, accounts, devices and data that you own or are expressly authorised to test. Do not access another person's data, exfiltrate information, perform denial-of-service or destructive testing, use social engineering, circumvent account controls, or publicly disclose an unremediated vulnerability before a reasonable opportunity for investigation and remediation. This policy does not authorise conduct prohibited by law or by a third-party service's terms.

5. Security incidents

If we confirm a security incident within systems or data for which the Study Director operators are responsible, we will take reasonable steps appropriate to the circumstances to contain the incident, investigate its cause and scope, preserve relevant evidence, reduce ongoing risk, remediate the affected component, and prevent recurrence where practicable. We will notify affected users, Google, the Data Protection Board of India, CERT-In, or other competent authorities when and to the extent required by applicable law, binding service terms, or a valid legal obligation.
